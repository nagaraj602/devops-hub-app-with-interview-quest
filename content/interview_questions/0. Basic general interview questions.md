<summary><strong>1. What was your team size and structure?</strong></summary>

**Answer:**
### 1. Direct Core Response
"Our overall engineering organization followed a cross-functional squad model supported by a centralized Platform/DevOps team. The engineering department consisted of ~42 total members:
- **1 Central Platform & DevOps Team (4 Engineers):** 1 Cloud Architect, 2 Senior DevOps Engineers, and 1 Automation Engineer.
- **5 Cross-Functional Feature Squads (~30 Software Developers):** ~6 developers per squad (Go, Java/Spring Boot microservices, and React frontend) handling Ingestion, Rule Evaluation, Anomaly Scoring, Case Queues, and Enforcement.

- **Product & Agile Leadership:** 2 Product Managers, 1 Scrum Master, and 1 Engineering Manager."

---

### 2. Organizational Models (Method 1 vs Method 2)
* **Method 1: Centralized Platform / SRE Team (Our Model)**
  - *Structure:* A dedicated DevOps team builds and maintains developer tooling, shared CI/CD pipelines, Kubernetes clusters, and cloud infrastructure as internal platform products.
  - *Pros:* Strict compliance, standardized security scanning (Trivy/SonarQube), centralized cloud cost controls, and reusable Helm/Terraform modules.
  - *Cons:* Risk of handoff bottlenecks if feature developers cannot self-service.
* **Method 2: Embedded DevOps Model (Decentralized Squads)**
  - *Structure:* 1 DevOps engineer embedded inside each software squad.
  - *Pros:* High domain knowledge of individual microservice business logic.
  - *Cons:* Tooling fragmentation, inconsistent pipeline patterns, and duplicated cloud resources.

---

### 3. Production Use Case & Collaboration
In our day-to-day workflow, our centralized DevOps team provided "Golden Paths" (standardized Jenkins Shared Libraries, pre-configured Helm charts, and Terraform modules). Feature squads had complete ownership over application logic and lower environment testing, while our DevOps team owned cluster reliability, zero-downtime release engineering, and multi-region AWS cloud governance.
</details>

* **Method 2: Functional Domain Ownership**
  - Alternatively, dividing by technical pillars: 2 engineers owning CI/CD & Artifacts, 2 engineers owning Kubernetes runtime & Cloud Networking. We found the Run vs Build rotation superior as it prevented burnout and eliminated knowledge silos.

<summary><strong>6. How many environments did you have?</strong></summary>

**Answer:**
### 1. Direct Core Response
"We maintained **4 distinct environments** to ensure reliable code promotion and defect isolation:
1. **DEV (Development):** Hosted on Amazon EKS. Fully automated continuous deployment triggered immediately upon merging feature PRs to the `dev` branch. Used by developers for microservice unit testing and rapid verification.
2. **QA (Quality Assurance):** Dedicated environment for QA SDETs to run automated functional test suites (REST Assured / PyTest) and contract verification. Deployed automatically upon merging code into `qa`.
3. **UAT / Staging (User Acceptance Testing):** An exact production mirror (same multi-AZ EKS topology, security groups, and data sanitization). Used for full end-to-end integration testing, shadow Kafka traffic replays, and performance load testing (k6/JMeter).
4. **PROD (Production):** High-availability multi-AZ cluster (18 worker nodes across 3 AZs). Strict manual promotion gate requiring CAB/Lead approval, deployed during scheduled maintenance windows with automated canary analysis."

---

### 2. Environment Isolation Approaches (Method 1 vs Method 2)
* **Method 1: Multi-Account AWS Architecture (Production Best Practice)**
  - *Setup:* Separate AWS Accounts managed under AWS Organizations: `Account-Dev/QA`, `Account-Staging`, `Account-Prod`.
  - *Benefits:* Absolute security blast radius isolation, independent IAM boundaries, and separate billing/cost allocation.
* **Method 2: Single Account Multi-VPC / Multi-Namespace**
  - *Setup:* Single AWS account using separate VPCs or Kubernetes namespaces.
  - *Trade-off:* Lower AWS management overhead, but higher risk of accidental credential overlap or quota exhaustion. We strictly followed Method 1 (Multi-Account).

---

### 3. Data Hygiene Across Environments
Production customer data was strictly prohibited from being copied to lower environments. Lower environments used synthetic mock data or anonymized datasets generated via automated data scrubbing scripts.

<summary><strong>8. How many servers did you manage?</strong></summary>

**Answer:**
### 1. Direct Core Response
"We treated infrastructure as **immutable cattle, not pets**. All servers were codified through Terraform and managed via Kubernetes:
- In **Production**, we ran an Amazon EKS cluster with **18 worker nodes** of type `m6i.4xlarge` (16 vCPUs, 64 GB RAM each) distributed across 3 Availability Zones (6 nodes per AZ), providing **288 total vCPUs** and **1,152 GB RAM**.

---

### 2. Compute Management Strategies
* **Strategy 1: Static EC2 Server Management (Legacy Pet Approach)**
  - Fixed server counts, manual patching via SSH, static IP assignments. High maintenance overhead.
* **Strategy 2: Cloud-Native Auto-Scaling Node Pools (Our Architecture)**
  - EKS Managed Node Groups with Launch Templates specifying Amazon Linux 2 / Bottlerocket AMIs.
  - Node replacement lifecycle: Nodes are never patched in place; new AMI versions are rolled out via rolling node replacement (`kubectl drain` -> terminate old node -> spawn new node).

---

### 3. Production Node Pool Segmentation
Our production cluster was segregated into 3 specialized node pools:
1. `ingress-pool` (4 nodes): High network bandwidth for ALB reverse proxies and Kafka consumers.
2. `compute-pool` (10 nodes): General microservice business logic with memory-to-CPU optimization.
3. `stateful-pool` (4 nodes): Fast NVMe/gp3 EBS storage for distributed cache and rule evaluation engines.

<summary><strong>35. Tell me about the most difficult Kubernetes issue you solved.</strong></summary>

**Answer:**
### 1. Direct Core Response (STAR Framework)
* **Situation:** In our Amazon EKS production cluster, microservices experienced intermittent, random 504 Gateway Timeouts and DNS lookup failures (`dial tcp: lookup my-service on 172.20.0.10:53: i/o timeout`) during sudden traffic spikes.
* **Investigation:**
  - Standard pod logs showed DNS timeouts, but CoreDNS pods showed normal CPU usage.
  - I inspected the Linux kernel networking metrics on our EC2 worker nodes using `conntrack` and discovered that Linux **Netfilter connection tracking table (`nf_conntrack`) was becoming exhausted**, causing the kernel to silently drop UDP DNS packets!
  - In addition, standard CoreDNS was overwhelmed by excessive single-request lookups because applications lacked DNS caching.
* **Resolution:**
  1. Deployed **NodeLocal DNSCache** as a DaemonSet across all EKS nodes to intercept DNS queries locally via a cache agent on node loopback IP (`169.254.20.10`), eliminating cross-node CoreDNS round-trips.
  2. Switched DNS resolution transport from UDP to TCP in `resolv.conf` to avoid conntrack UDP race conditions.
  3. Increased kernel conntrack limits (`sysctl -w net.netfilter.nf_conntrack_max=1048576`).
* **Result:** DNS resolution latency plummeted from 120ms to under 1.5ms, and the 504 Gateway Timeouts were 100% eliminated.
</details>

<summary><strong>36. Terraform state gets deleted. What happens?</strong></summary>

**Answer:**
### 1. Direct Core Response
"The Terraform state file (`terraform.tfstate`) is the single source of truth mapping your declarative HCL code to real-world cloud resource IDs in AWS. **If the state file is deleted, Terraform suffers complete amnesia**:
- Terraform code still exists, and your AWS resources (VPC, EC2, RDS) are still running in the cloud, but Terraform no longer knows they belong to it.
- If an engineer executes `terraform apply`, Terraform will assume no infrastructure exists and attempt to **create all resources from scratch**, causing collision errors (e.g. 'VPC CIDR already exists') or provisioning duplicate infrastructure and doubling cloud costs."

---

### 2. Recovery Strategies (Method 1 vs Method 2)
* **Method 1: Restore from S3 Version History (Immediate & Best Practice)**
  - Because we maintain state in an Amazon S3 bucket with **Versioning Enabled**, a deletion simply places a delete marker.
  - We simply remove the S3 delete marker or restore the previous version from S3 version history. State is fully restored in 2 minutes with zero drift.
* **Method 2: Reconstruction via `terraform import` (Disaster Recovery)**
  - If state is permanently gone with no backups, you must run `terraform import` resource by resource (e.g., `terraform import aws_vpc.main vpc-0123456789`). This is time-consuming and error-prone.
</details>

<summary><strong>41. Why shouldn't we just use `latest` for Docker images?</strong></summary>

**Answer:**
### 1. Direct Core Response
"Using the `:latest` tag in production violates the fundamental DevOps principle of **immutability and idempotency**:
1. **Mutable Tag Ambiguity:** `:latest` is merely a pointer that changes whenever a new image is pushed. You have no guarantee what code is actually running inside the container.
2. **Breaks Kubernetes Rollbacks:** If a pod restarts or scales out, Kubernetes checks if it has `:latest` locally. If `imagePullPolicy` is `Always`, it pulls the new `:latest` (which might contain breaking changes), causing different pods in the same Deployment to run different versions of code!
3. **Traceability & Auditing:** With `:latest`, it is impossible to map a running production container back to the specific Git commit that generated it.

---

### 2. Best Practice Image Tagging Strategy
* **Tag with Git Commit SHA:** `myapp:git-7a8f12c`
* **Tag with Semantic Versioning:** `myapp:v2.4.1`
* **Deploy via Immutable SHA256 Digest (Most Secure):**
```yaml
image: 123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp@sha256:4f5e8d9...
```
This guarantees 100% consistency across all cluster nodes and makes rollbacks deterministic."
</details>
