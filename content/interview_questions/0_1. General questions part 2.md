# DevOps Interview Scenarios and Strategic Answers

---

## 1. The Production Break

<details markdown="1">
<summary><strong>"A developer pushes bad code that breaks production, but your CI/CD pipeline deployed it. Whose fault is it?"</strong></summary>

*   **The Trap:** Junior candidates will immediately say "It's the developer's fault for writing bad code." This shows a toxic, finger-pointing mentality.
*   **Strong Answer:** "I don't look at it as a human failure; I look at it as a system failure. If bad code made it to production, it means our pipeline allowed it. While the developer wrote the bug, DevOps owns the delivery mechanism. My immediate focus would be on rolling back to restore service. Once things are stable, I would sit down with the developer to figure out what automated test, linting rule, or deployment gate we can add to the pipeline so that this specific class of bug is caught before it ever reaches production again."

> **Key takeaway:** Blame systems, not people.

</details>

## 2. The Alert Storm

<details markdown="1">
<summary><strong>"You have 5 critical monitoring alerts firing at the exact same time. How do you prioritize?"</strong></summary>

*   **The Trap:** Trying to fix all of them at once, or picking the one that looks "easiest."
*   **Strong Answer:** "I prioritize strictly based on customer and business impact. First, I look for the alert affecting the core revenue-generating service or the path that impacts the most users—like a database outage or the API gateway going down. Second, I check if any of the alerts are cascading failures (e.g., the database went down, causing 4 other microservices to alert). I would focus entirely on fixing the root service, as that will naturally resolve the downstream alerts. If I'm overwhelmed, I immediately escalate and pull in other engineers to divide the investigation."

> **Key takeaway:** Prioritize blast radius and revenue impact. Look for cascading failures.

</details>

## 3. Pipeline Friction

<details markdown="1">
<summary><strong>"Developers complain that your security and testing checks are slowing down their deployments too much. What do you do?"</strong></summary>

*   **The Trap:** Acting like a dictator ("Security is non-negotiable") or a pushover ("I'll remove the tests").
*   **Strong Answer:** "I would take their feedback seriously because the goal of DevOps is to enable developers, not block them. I'd sit down with them to identify exactly where the bottleneck is. Are the Docker builds taking too long? Are end-to-end tests flaky? We could optimize this by running tests in parallel in Jenkins, caching Docker layers, or moving heavy security scans to run asynchronously on PRs rather than blocking the main deployment branch. We shouldn't compromise on security, but we can absolutely optimize the speed of the pipeline."

> **Key takeaway:** Show empathy. Solve the speed issue technically without lowering security standards.

</details>

## 4. Compromised Secrets

<details markdown="1">
<summary><strong>"You find hardcoded AWS credentials in a developer's recent Git commit. What is your immediate action?"</strong></summary>

*   **The Trap:** Saying "I will delete the code and tell the developer." If it's committed to Git, it's already compromised.
*   **Strong Answer:** "Once a secret is committed, it must be considered compromised. Deleting the code is not enough because it remains in the Git history. My immediate action is to revoke and rotate the exposed AWS credentials in the AWS console to stop any potential abuse. Only after the keys are invalidated would I remove them from the codebase and rewrite the Git history if necessary. Afterward, I'd work with the developer to implement a secret manager, like AWS Secrets Manager or HashiCorp Vault, and add a tool like GitLeaks to our pipeline to catch hardcoded secrets before they are committed."

> **Key takeaway:** Revoke first, delete second, automate prevention third.

</details>

## 5. Admitting Failure

<details markdown="1">
<summary><strong>"Tell me about a time you broke production or made a major mistake."</strong></summary>

*   **The Trap:** Saying "I never have" (which means you have no experience or you're lying), or blaming someone else.
*   **Strong Answer:** "In one of my projects, I was updating a Terraform configuration for an existing database. I misunderstood how a specific parameter worked, and applying it caused the database instance to reboot during peak hours, causing a brief outage. I immediately notified the team, verified the system recovered after the reboot, and checked the application logs for data loss. What I learned from that was never to run `terraform apply` on stateful resources without deeply reviewing the `terraform plan` output with a senior engineer. I also added a lifecycle rule to `prevent_destroy` on critical databases."

> **Key takeaway:** Admit a realistic mistake, focus on how quickly you communicated, and explain the permanent lesson you learned.

</details>

## 6. The Black Box Legacy System

<details markdown="1">
<summary><strong>"You are assigned to troubleshoot a legacy system that keeps crashing. There is zero documentation and the original engineers have left. Where do you start?"</strong></summary>

*   **The Trap:** Complaining about the lack of documentation or saying you'd rewrite the whole thing.
*   **Strong Answer:** "Lack of documentation is common, so I would treat it as an investigation. I'd start from the outside in. First, I'd look at the infrastructure layer—is it running out of CPU, memory, or disk space when it crashes? Next, I'd look at the application logs and OS logs like `/var/log/syslog` right before the crash timestamp. I would also map out its dependencies by checking active network connections. As I investigate and figure out how it works, I would write the missing documentation myself. Complaining about the lack of docs doesn't fix the server, so I just focus on discovering the architecture layer by layer."

> **Key takeaway:** Show a methodical, analytical approach and a willingness to leave things better than you found them.

</details>

## 7. Patience with Modernization

<details markdown="1">
<summary><strong>"We still have a lot of manual, legacy deployments here. We aren't fully using Kubernetes or CI/CD yet. Are you okay with that?"</strong></summary>

*   **The Trap:** Sounding arrogant ("I only work with modern tech") or disappointed. They are testing if you have the patience to do the actual work of transformation.
*   **Strong Answer:** "Absolutely. I understand that real-world businesses have legacy systems that are critical to revenue, and you can't just flip a switch to Kubernetes overnight. I actually enjoy the migration process. I would be happy to maintain the legacy deployments while looking for small, incremental ways to automate them. For example, maybe we can't move to Kubernetes today, but we could start by containerizing the application or writing a simple bash script to automate the manual deployment steps. My goal is to deliver business value, not just play with the newest tools."

> **Key takeaway:** Demonstrate patience, pragmatism, and a step-by-step approach to modernization.

</details>
