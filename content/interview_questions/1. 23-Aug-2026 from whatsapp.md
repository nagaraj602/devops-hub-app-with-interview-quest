<summary><strong>Difference between NACL & SG.</strong></summary>

**Answer:**

| Feature | Security Group (SG) | Network ACL (NACL) |
| :--- | :--- | :--- |
| **Level** | Instance level (EC2, ENI, ALB) | Subnet level (Acts as a subnet firewall) |
| **State** | **Stateful** (Inbound return traffic is automatically allowed outbound) | **Stateless** (Outbound return traffic must be explicitly defined in outbound rules) |
| **Rule Type** | **Allow rules only** (Default denies everything not explicitly allowed) | **Allow and Deny rules** |
| **Evaluation** | All rules are evaluated before deciding to permit traffic | Rules are evaluated in strict **numerical order** (lowest number first) |
| **Default** | Default SG allows all outbound and blocks all inbound | Default NACL allows all inbound and outbound traffic |
</details>

<summary><strong>Task to patch an EC2 instance which is in a private subnet.</strong></summary>

**Answer:**
To patch an EC2 instance in a private subnet without exposing it to the public internet:
1. **Outbound Internet Connectivity:** Configure a **NAT Gateway** in a public subnet and add a default route (`0.0.0.0/0 -> nat-gateway-id`) to the private subnet route table so the instance can download OS update packages (`yum update` / `apt upgrade`).
2. **AWS Systems Manager (SSM) Patch Manager (Zero Internet / Private Way):**
   - Attach the IAM role `AmazonSSMManagedInstanceCore` to the EC2 instance.
   - Configure **VPC Endpoints (PrivateLink)** for SSM (`ssm`, `ssmmessages`, `ec2messages`) so SSM traffic never traverses the public internet.
   - Use **AWS Systems Manager Patch Manager** with an approved Patch Baseline to scan and automatically install missing patches during a scheduled maintenance window without needing SSH access or bastion hosts.
</details>

<details markdown="1">
<summary><strong>S3 Endpoints.</strong></summary>

**Answer:**
S3 Endpoints enable private connectivity between your Amazon VPC and Amazon S3 without requiring an Internet Gateway, NAT Gateway, VPN, or Direct Connect.
*   **Gateway Endpoint (Free):** Implemented via a routing entry in the VPC Route Table targeting `pl-xxxxxx` (AWS S3 Prefix List). Highly recommended for high-throughput, internal VPC-to-S3 traffic.
*   **Interface Endpoint (PrivateLink - Paid per hour + data processing):** Creates an Elastic Network Interface (ENI) with a private IP inside your subnet. Allows access to S3 from on-premises networks via VPN/Direct Connect or from peered VPCs.
</details>

<details markdown="1">
<summary><strong>Are S3 Endpoints cached locally?</strong></summary>

**Answer:**
S3 Endpoints are not "cached" in the traditional sense — they work differently:
*   **Gateway Endpoints:** These are routing entries in your VPC Route Table. When your EC2 instance sends traffic to S3, the route table directs it through the Gateway Endpoint automatically — no caching involved, it's just a network route.
*   **Interface Endpoints:** These create a private IP address (ENI) inside your subnet. Your DNS resolves `s3.us-east-1.amazonaws.com` to this private IP instead of the public one. The DNS response is cached briefly by your system's DNS resolver (usually for 60 seconds based on TTL), but the actual data transfer goes directly to S3 each time.
</details>

<details markdown="1">
<summary><strong>VPC Endpoints.</strong></summary>

**Answer:**
VPC Endpoints allow private communication between your VPC and supported AWS services (or third-party hosted services) through AWS PrivateLink without public IP addresses or traversing the internet.
*   **Gateway Endpoints:** Supported only for **S3** and **DynamoDB** (Route Table target).
*   **Interface Endpoints:** Supported for over 100+ AWS services (ECR, SSM, Secrets Manager, CloudWatch, SQS, SNS) powered by AWS PrivateLink with private ENIs and security group enforcement.
</details>

<details markdown="1">
<summary><strong>What are the layers in Docker?</strong></summary>

**Answer:**
Each instruction in a `Dockerfile` (`FROM`, `RUN`, `COPY`, `ADD`) creates an immutable, read-only filesystem layer.
*   **Layer Caching:** Docker caches unchanged layers. If a layer changes, all subsequent layers are rebuilt.
*   **Union File System (Overlay2):** Stacks all read-only image layers together and adds a single thin, writable **Container Layer** on top when a container runs.
*   **Best Practice:** Combine multiple `RUN` commands with `&& \` and clean up package caches (`rm -rf /var/lib/apt/lists/*`) in the same layer to minimize final image size.
</details>

<details markdown="1">
<summary><strong>Why use ENTRYPOINT & not CMD?</strong></summary>

**Answer:**
*   **`CMD`:** Sets default arguments or a default command that can be **completely overridden** by command-line arguments passed when running `docker run <image> <new_command>`.
*   **`ENTRYPOINT`:** Sets the **fixed executable process** that will always run when the container starts. Any CLI arguments passed to `docker run` are appended as arguments to the `ENTRYPOINT`.
*   **Best Practice Pattern:** Use `ENTRYPOINT` to define the binary (e.g., `ENTRYPOINT ["nginx"]`) and `CMD` to provide default parameters (e.g., `CMD ["-g", "daemon off;"]`), allowing users to easily customize flags while keeping the container purpose fixed.
</details>

<details markdown="1">
<summary><strong>Explain multistage Dockerfile.</strong></summary>

**Answer:**
A multi-stage `Dockerfile` uses multiple `FROM` instructions to separate the **build environment** (which contains compilers, SDKs, Maven/Gradle, Git) from the **final runtime environment** (which contains only the compiled binary and runtime dependencies).

```dockerfile
# Stage 1: Build stage
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: Production runtime stage
FROM eclipse-temurin:17-jre-alpine
WORKDIR /app
COPY --from=builder /app/target/app.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```
**Benefits:** Reduces image size drastically (e.g., from 800MB to 120MB), improves build caching, and removes build tools and vulnerabilities from the production container.
</details>

<details markdown="1">
<summary><strong>What is Docker Compose?</strong></summary>

**Answer:**
Docker Compose is a tool for defining and running multi-container Docker applications using a single YAML file (`docker-compose.yml`). Instead of running multiple `docker run` commands, you define everything in one file and manage it together.

**Example `docker-compose.yml`:**
```yaml
version: '3.8'
services:
  frontend:
    image: nginx:alpine
    ports:
      - "80:80"
    depends_on:
      - backend

  backend:
    image: myapp:latest
    ports:
      - "8080:8080"
    environment:
      - DB_HOST=database
      - DB_PORT=5432
    depends_on:
      - database

  database:
    image: postgres:15
    environment:
      - POSTGRES_DB=myapp
      - POSTGRES_USER=admin
      - POSTGRES_PASSWORD=secret
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:
```

**Common Commands:**
```bash
docker compose up -d       # Start all containers in background
docker compose down        # Stop and remove all containers
docker compose logs -f     # Follow logs from all services
docker compose ps          # List running containers
docker compose restart     # Restart all services
```

**Why use it:** Instead of running 3 separate `docker run` commands with network and volume flags, one `docker compose up -d` starts everything with proper networking, volumes, and dependency ordering. Widely used for local development and staging environments.
</details>

<summary><strong>ClusterIP vs NodePort.</strong></summary>

**Answer:**
*   **ClusterIP (Default):** Exposes the Service on an internal IP accessible **only within the Kubernetes cluster**. Used for inter-service communication (backend APIs, internal databases).
*   **NodePort:** Exposes the Service on each Node's IP at a static port in the range `30000-32767`. Traffic sent to `<NodeIP>:<NodePort>` is forwarded to internal pods. Used for direct debugging or exposing services behind external physical load balancers.
</details>

<summary><strong>I have an ECR repo and we have Docker images on-premises. How will you pull those images? What are the steps we do in the manifest file?</strong></summary>

**Answer:**
To pull images from AWS ECR into an on-premises Kubernetes cluster:
1. **Generate AWS ECR Login Token:**
   ```bash
   aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <aws_account_id>.dkr.ecr.<region>.amazonaws.com
   ```
2. **Create Kubernetes `docker-registry` Secret:**
   ```bash
   kubectl create secret docker-registry ecr-secret \
     --docker-server=<aws_account_id>.dkr.ecr.<region>.amazonaws.com \
     --docker-username=AWS \
     --docker-password=$(aws ecr get-login-password --region <region>) \
     --namespace=<target-namespace>
   ```
3. **Reference the Secret in the Deployment Manifest:**
   ```yaml
   apiVersion: apps/v1
   kind: Deployment
   metadata:
     name: my-app
   spec:
     template:
       spec:
         imagePullSecrets:
           - name: ecr-secret
         containers:
           - name: app
             image: <aws_account_id>.dkr.ecr.<region>.amazonaws.com/my-repo:v1.0.0
   ```
*(Note: Since ECR auth tokens expire every 12 hours, configure an automated CronJob or use AWS IAM Roles Anywhere to refresh the secret periodically).*
</details>

<summary><strong>For authentication, what type of objects do we create in Kubernetes (K8s)?</strong></summary>

**Answer:**
Kubernetes uses several objects for authentication and authorization:
1. **ServiceAccounts:** These are used by pods/applications running inside the cluster to talk to the Kubernetes API. Every namespace has a default ServiceAccount, and you can create custom ones for specific permissions.
   ```bash
   kubectl create serviceaccount my-app-sa -n my-namespace
   ```
2. **RBAC (Role-Based Access Control):** This is how we control *who can do what* in the cluster:
   *   **`Role`:** Defines permissions (like `get`, `list`, `create`, `delete`) within a specific namespace.
   *   **`ClusterRole`:** Same as Role but works across all namespaces.
   *   **`RoleBinding`:** Connects a Role to a user or ServiceAccount within a namespace.
   *   **`ClusterRoleBinding`:** Connects a ClusterRole to a user or ServiceAccount cluster-wide.

**Example — Give a ServiceAccount read-only access to pods:**
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: my-namespace
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: my-namespace
subjects:
- kind: ServiceAccount
  name: my-app-sa
  namespace: my-namespace
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
For human users, we typically use AWS IAM Authenticator (in EKS) which maps IAM roles to Kubernetes RBAC groups — so developers authenticate with their AWS credentials.
</details>

<summary><strong>What are Secrets in K8s?</strong></summary>

**Answer:**
Secrets in Kubernetes store sensitive data like passwords, API keys, and TLS certificates. Here's how we manage them:

**Method 1: Kubernetes Secrets (Simple Approach)**
```bash
# Create a secret from command line
kubectl create secret generic db-credentials \
  --from-literal=username=admin \
  --from-literal=password=MyP@ssw0rd \
  -n my-namespace
```

Or using a YAML file:
```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: my-namespace
type: Opaque
data:
  username: YWRtaW4=          # base64 encoded "admin"
  password: TXlQQHNzdzByZA==  # base64 encoded "MyP@ssw0rd"
```

**Using the secret in a Pod:**
```yaml
# As environment variables
env:
- name: DB_USER
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: username
- name: DB_PASS
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: password

# Or mount as files
volumes:
- name: secret-volume
  secret:
    secretName: db-credentials
```

**Method 2: AWS Secrets Manager + External Secrets Operator (Production Best Practice)**
In production, we don't store secrets in Git. Instead:
1. Store secrets in **AWS Secrets Manager**
2. Install **External Secrets Operator (ESO)** in the cluster
3. ESO automatically syncs secrets from AWS into Kubernetes Secret objects

This way, secrets are centrally managed, encrypted, audited, and never committed to source code.

*   **Security Best Practices:**
    *   Enable KMS encryption at rest in `etcd`.
    *   Use RBAC to restrict access to Secrets.
    *   Integrate with **AWS Secrets Manager / HashiCorp Vault** using the **External Secrets Operator (ESO)** or CSI Secrets Store Driver.
</details>

<details markdown="1">
<summary><strong>What to do if kubelet is not working?</strong></summary>

**Answer:**
Troubleshooting steps when `kubelet` fails on a worker node:
1. **Check Kubelet Status & Logs:**
   ```bash
   sudo systemctl status kubelet
   sudo journalctl -u kubelet -n 100 --no-pager
   ```
2. **Check Container Runtime:** Verify if `containerd` or `cri-o` is running (`systemctl status containerd`).
3. **Check Node Disk & Memory:** Verify disk space (`df -h`) and memory (`free -m`). Kubelet stops if disk pressure or out-of-memory triggers eviction.
4. **Verify Certificates:** Check if client certificates in `/var/lib/kubelet/pki/` have expired.
5. **Check API Server Connectivity:** Verify the node can resolve and reach the Kubernetes API endpoint via port 6443 (`curl -k https://<api-server>:6443/healthz`).
6. **Restart Services:**
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl restart containerd kubelet
   ```
</details>

<details markdown="1">
<summary><strong>Handle memory issues in the manifest file.</strong></summary>

**Answer:**
In Kubernetes manifests, configure memory requests and limits under `resources`:
```yaml
resources:
  requests:
    memory: "256Mi"
    cpu: "250m"
  limits:
    memory: "512Mi"
```
*   **`requests`:** Guaranteed memory allocation scheduled by Kubernetes.
*   **`limits`:** Hard threshold. If a container exceeds its memory limit, the Linux kernel terminates it with **OOMKilled (Exit Code 137)**.
*   **Best Practices:**
    *   Set JVM heap parameters (`-XX:MaxRAMPercentage=75.0`) to avoid JVM memory escaping container bounds.
    *   Implement **Vertical Pod Autoscaler (VPA)** for automated right-sizing.
</details>

<summary><strong>EKS overview.</strong></summary>

**Answer:**
Amazon Elastic Kubernetes Service (EKS) is a managed Kubernetes service that runs the Kubernetes control plane across multiple AWS Availability Zones for high availability.
*   **Control Plane:** AWS manages etcd, API server, and master node patching, scaling, and backups.
*   **Data Plane (Worker Nodes):**
    *   **Managed Node Groups:** EC2 instances provisioned and updated automatically by EKS.
    *   **Self-Managed Nodes:** Custom EC2 instances registered to EKS.
    *   **AWS Fargate:** Serverless pod execution without managing EC2 nodes.
*   **Integrations:** Native IAM integration via **IRSA (IAM Roles for Service Accounts)**, VPC CNI for native VPC IP assignment per Pod, and AWS Load Balancer Controller.

<summary><strong>What are roles in Ansible?</strong></summary>

**Answer:**
Ansible roles provide a standardized, reusable directory structure to organize tasks, variables, files, templates, and handlers into modular units. Instead of putting hundreds of lines in a single playbook, roles allow you to break configurations into reusable components.

**Standard Directory Structure (created via `ansible-galaxy init <role_name>`):**
```text
my_role/
├── tasks/         # Main list of tasks executed by the role (main.yml)
├── handlers/      # Handlers triggered by notify (e.g., restart service)
├── templates/     # Jinja2 template files (.j2) with dynamic variables
├── files/         # Static files copied to target hosts without modification
├── vars/          # High-priority variables for this role
├── defaults/      # Default variables with lowest priority (can be easily overridden)
└── meta/          # Role metadata and dependencies
```

**How to call a role in a playbook:**
```yaml
---
- name: Deploy Web Servers
  hosts: webservers
  become: yes
  roles:
    - role: nginx
      vars:
        nginx_port: 8080
    - role: common_security
```
**Why use roles:**
* **Reusability:** You write an Nginx or Jenkins role once and reuse it across Dev, Staging, and Prod.
* **Maintainability:** Team members can work on individual role folders without stepping on each other's code.
* **Separation of concerns:** Configuration logic (tasks) is kept separate from dynamic data (templates/vars).
</details>

<details markdown="1">
<summary><strong>What are templates?</strong></summary>

**Answer:**
Templates in Ansible allow you to generate dynamic configuration files on managed hosts using the **Jinja2** templating engine (`.j2`). Unlike the `copy` module (which only moves static, unchanged files), templates substitute variables, facts, conditionals, and loops before placing the file on the remote server.

**Example: Jinja2 Template (`templates/nginx.conf.j2`):**
```nginx
server {
    listen {{ http_port | default(80) }};
    server_name {{ server_domain }};

    location / {
        proxy_pass http://{{ backend_host }}:{{ backend_port }};
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**Example: Ansible Task using `template` module:**
```yaml
- name: Deploy dynamic Nginx config from template
  template:
    src: templates/nginx.conf.j2
    dest: /etc/nginx/conf.d/app.conf
    owner: root
    group: root
    mode: '0644'
  notify: Restart Nginx
```

**Key difference:**
* **`copy`:** Use when the file content is 100% identical on every server (e.g., static license key, binary).
* **`template`:** Use when the configuration depends on environment variables, hostname, IP address, or environment (Dev vs Prod).
</details>

<summary><strong>How to troubleshoot ImagePullBackOff error?</strong></summary>

**Answer:**
"An `ImagePullBackOff` indicates that Kubernetes cannot pull the specified container image and is waiting with exponential backoff delay.
- **Step 1: Inspect Pod Events:**
  ```bash
  kubectl describe pod <pod-name> -n <namespace>
  ```
  Check the `Events:` section at the bottom for the exact failure code (e.g. 401 Unauthorized, 404 Not Found, 429 Too Many Requests).
- **Common Causes & Fixes:**
  1. **Image Name or Tag Typo:** Tag does not exist in registry (e.g., `:v1.2` instead of `:1.2.0`). Verify tag in ECR/DockerHub.
  2. **Missing/Expired Registry Authentication:** For private registries, verify `imagePullSecrets` is defined in the Deployment spec. Note: AWS ECR tokens expire after 12 hours.
  3. **VPC Network / Subnet Routing:** Worker nodes in private subnets cannot reach the registry because the NAT Gateway is misconfigured or VPC Endpoints for ECR (`ecr.api` and `ecr.dkr`) are missing.

<details markdown="1">
<summary><strong>How to troubleshoot CrashLoopBackOff error?</strong></summary>

**Answer:**
"A `CrashLoopBackOff` means the container process starts, crashes, and Kubelet restarts it in a loop with exponential backoff delay.
- **Step-by-Step Troubleshooting:**
  1. **Check Previous Crash Logs:**
     ```bash
     kubectl logs <pod-name> -n <namespace> --previous
     ```
  2. **Check Pod Exit Code:**
     ```bash
     kubectl describe pod <pod-name> -n <namespace>
     ```
     Inspect `Last State: Terminated` and check `Exit Code`:
     - **Exit Code 137:** Pod was killed by **OOMKilled** (Out of Memory). Solution: Increase `resources.limits.memory`.
     - **Exit Code 1 / Application Exception:** Missing environment variable, bad config file syntax, or database connection timeout.
     - **Exit Code 0:** Container completed and exited because there was no foreground process keeping it alive.
     - **Exit Code 143:** Graceful shutdown (SIGTERM), often triggered by failing Liveness Probes.
  3. **Debug Interactively:** Temporarily override container command with `command: ["sleep", "3600"]`, apply, and run `kubectl exec -it <pod> -- sh` to inspect local configs, environment variables, and network connectivity.
</details>

<summary><strong>What is equilibrium index in Python?</strong></summary>

**Answer:**
The equilibrium index of an array is an index `i` such that the sum of elements at lower indices is equal to the sum of elements at higher indices.
```python
def find_equilibrium_index(arr):
    total_sum = sum(arr)
    left_sum = 0
    for i, num in enumerate(arr):
        total_sum -= num
        if left_sum == total_sum:
            return i
        left_sum += num
    return -1

# Example: [1, 3, 5, 2, 2] -> sum left of index 2 (1+3=4) == sum right of index 2 (2+2=4) -> returns 2
```

<summary><strong>Explain to me about Ansible playbooks.</strong></summary>

**Answer:**
An **Ansible Playbook** is a YAML file where we define the desired configuration state of target machines. It maps a group of hosts from your inventory to specific tasks (actions like installing packages, managing services, copying files) executed sequentially over SSH without needing any client-side agents.

**Structure of a Playbook:**
A playbook contains one or more **plays**. Each play has:
1. `hosts`: Target machines from inventory (e.g. `webservers`, `all`)
2. `become: yes`: Privilege escalation (sudo)
3. `vars`: Variables used in tasks
4. `tasks`: Ordered list of module actions
5. `handlers`: Conditional tasks triggered only when a task reports `changed` (e.g., restart service after config change)

**Real-world Example Playbook (`setup_webserver.yml`):**
```yaml
---
- name: Configure Nginx Web Server and Deploy App
  hosts: webservers
  become: yes
  vars:
    app_port: 80
    doc_root: /var/www/html

  tasks:
    - name: Update apt cache and install Nginx
      apt:
        name: nginx
        state: latest
        update_cache: yes

    - name: Ensure document root directory exists
      file:
        path: "{{ doc_root }}"
        state: directory
        owner: www-data
        group: www-data
        mode: '0755'

    - name: Deploy index.html from template
      template:
        src: templates/index.html.j2
        dest: "{{ doc_root }}/index.html"
        mode: '0644'
      notify: Reload Nginx

    - name: Ensure Nginx service is running and enabled on boot
      service:
        name: nginx
        state: started
        enabled: yes

  handlers:
    - name: Reload Nginx
      service:
        name: nginx
        state: reloaded
```

**Executing the Playbook:**
```bash
# Syntax check
ansible-playbook setup_webserver.yml --syntax-check

ansible-playbook setup_webserver.yml -i inventory.ini --check --diff

# Execute the playbook
ansible-playbook setup_webserver.yml -i inventory.ini
```

**Key Advantages:**
* **Idempotency:** Running it once or ten times produces the exact same state without unintended side-effects.
* **Agentless:** Works entirely over standard SSH and Python.

### Method 2: Process / Service Watchdog (Auto-Restart if Dead)
```bash
#!/bin/bash
# Description: Check if Nginx is running. If not, restart it and log the incident.

SERVICE="nginx"
LOG_FILE="/var/log/service_watchdog.log"

if ! systemctl is-active --quiet "$SERVICE"; then
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] WARNING: $SERVICE is DOWN! Attempting restart..." >> "$LOG_FILE"
    
    sudo systemctl restart "$SERVICE"
    
    # Verify if restart was successful
    if systemctl is-active --quiet "$SERVICE"; then
        echo "[$(date '+%Y-%m-%d %H:%M:%S')] SUCCESS: $SERVICE was restarted successfully." >> "$LOG_FILE"
    else
        echo "[$(date '+%Y-%m-%d %H:%M:%S')] CRITICAL: $SERVICE failed to restart!" >> "$LOG_FILE"
    fi
fi
```
*Why this code is good:*
* Uses `systemctl is-active --quiet` which returns exit code `0` (active) or non-zero (inactive) cleanly without messy string parsing.
* Appends timestamps to `/var/log` for audit trails and incident post-mortems.
