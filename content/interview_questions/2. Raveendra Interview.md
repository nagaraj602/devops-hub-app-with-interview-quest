### Scenario: Critical Payment Service Failing with `CrashLoopBackOff` After a Release

### 1. Problem Description:
Immediately following a scheduled release to the staging environment, the payment microservice failed to start. New pods kept restarting repeatedly and entered the `CrashLoopBackOff` state, causing transaction endpoints to fail.

### 2. Systematic Troubleshooting Steps:
1. **Checked Pod Status:**
   ```bash
   kubectl get pods -n staging -l app=payment-service
   ```
   *Result:* Showed status `CrashLoopBackOff` with a restart count of 4.
2. **Inspected Events:**
   ```bash
   kubectl describe pod <payment-pod-name> -n staging
   ```
   *Result:* The Events section showed that the container was created and started successfully, but immediately terminated with **Exit Code 1**.
3. **Checked Container Logs (Including Previous Crashed Instance):**
   ```bash
   kubectl logs <payment-pod-name> -n staging --previous
   ```
   *Result:* Found fatal application crash log:
   `Fatal Error: Missing required environment variable 'PAYMENT_GATEWAY_API_KEY'. Application cannot initialize.`
4. **Inspected Secret & Deployment Manifest:**
   - Inspected the deployment YAML: found the developers added a reference to a new Secret key `PAYMENT_GATEWAY_API_KEY`.
   - Inspected the Kubernetes Secret:
     ```bash
     kubectl get secret payment-secrets -n staging -o yaml
     ```
   *Result:* The secret in the namespace had not been updated with the new key name.

### 3. Resolution:
1. Added the missing `PAYMENT_GATEWAY_API_KEY` key and its value to the `payment-secrets` Kubernetes Secret.
2. Restarted the deployment rollout:
   ```bash
   kubectl rollout restart deployment payment-service -n staging
   ```
3. Verified the new pods started cleanly, passed readiness probes (`1/1 Running`), and logs confirmed successful connection.
4. **Preventative Action:** Updated the Helm chart pre-deploy validation checks to verify required secrets exist before starting the upgrade.

**Answer:**
### Scenario: Live Ingress 502 Bad Gateway Outage Due to Readiness Probe Misconfiguration

### 1. Problem Description:
During a daytime minor release of the customer profile service on a live cluster, users started experiencing intermittent **502 Bad Gateway** errors when accessing `/profile` endpoints.

### 2. Live Investigation Steps:
1. **Checked Ingress Controller Logs:**
   ```bash
   kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=100
   ```
   *Result:* Saw multiple upstream errors: `[error] 1234#1234: *5678 no live upstreams while connecting to upstream: "profile-service-8080"`.
2. **Checked Service Endpoints:**
   ```bash
   kubectl get endpoints profile-service -n prod
   ```
   *Result:* The `ENDPOINTS` column was **`<none>`**, meaning no pods were receiving traffic from the Service.
3. **Checked Pod States:**
   ```bash
   kubectl get pods -n prod -l app=profile-service
   ```
   *Result:* The pods were in `Running` status, but the `READY` column displayed **`0/1`**.
4. **Inspected Pod Diagnostics:**
   ```bash
   kubectl describe pod <profile-pod-name> -n prod
   ```
   *Result:* The Events section showed repeating warnings:
   `Warning Unhealthy 10s kubelet Readiness probe failed: HTTP probe failed with statuscode: 404`

### 3. Root Cause:
The application development team had updated their health endpoint path from `/health` to `/actuator/health`, but the Helm chart `values.yaml` was still configured to probe `/health`. Because the readiness probe returned 404, Kubernetes correctly did not add the pods to the Service endpoints, resulting in 502 Bad Gateway at the Ingress layer.

### 4. Resolution:
1. Immediately patched the deployment's readiness probe path:
   ```bash
   kubectl patch deployment profile-service -n prod --type='json' -p='[{"op": "replace", "path": "/spec/template/spec/containers/0/readinessProbe/httpGet/path", "value": "/actuator/health"}]'
   ```
2. Pods passed the readiness probe within 10 seconds (`1/1 READY`).
3. The Service endpoints immediately repopulated, and the 502 Bad Gateway errors dropped to zero.
4. Updated the version-controlled Helm chart to ensure future releases stayed consistent.
</details>

<details>
<summary><strong>↳ Follow-up: Why were you checking the request flow and the Ingress controller configuration as part of this troubleshooting process?</strong></summary>

**Answer:**
Checking the request flow and the Ingress controller is the most efficient troubleshooting starting point because **the Ingress controller acts as the front door (gateway)** to the entire Kubernetes cluster.

---

### 1. Understanding the Kubernetes Ingress Request Flow:
Incoming traffic follows a strict multi-layer path:
`Client Request` ➔ `Cloud Load Balancer (ALB)` ➔ `Ingress Controller Pod (NGINX/Traefik)` ➔ `Ingress Resource Routing Rules` ➔ `Kubernetes Service (ClusterIP)` ➔ `Pod Endpoints (Container port)`

---

### 2. Reasons for Checking Ingress & Request Flow:
1. **Quickly Isolates the Problem Layer:**
   - If the request never reaches the Ingress controller, the issue lies in **external DNS (Route 53) or Cloud Load Balancer listeners**.
   - If the Ingress controller receives the request but returns an error, its access logs immediately pinpoint which layer failed.
2. **Explains the Meaning of HTTP Status Codes:**
   - **404 Not Found (from Ingress):** Ingress host or path rule does not match the requested URL.
   - **502 Bad Gateway / 503 Service Unavailable (from Ingress):** The Ingress matched the route, but the target Service has **zero active endpoints** or the pod refused the connection.
   - **504 Gateway Timeout (from Ingress):** The pod received the request but took too long to respond (downstream database lock, slow query, or timeout).
3. **Validates Routing Rules and SSL/TLS:**
   - Confirms that TLS certificates are valid and not expired.
   - Verifies that URL rewrites, host header rules, and target ports align with what the backend Service expects.
</details>

<summary><strong>↳ Follow-up: Can you walk me through the exact steps you followed to troubleshoot the pod deployment issue in Kubernetes?</strong></summary>

**Answer:**
When troubleshooting a pod deployment issue in Kubernetes, I follow a systematic, step-by-step diagnostic workflow:

---

### Step 1: Check Pod Status and Namespaces
Run `kubectl get pods` to identify the current state of the pods and how many replicas are ready:
```bash
kubectl get pods -n <namespace> -o wide
```
Look for common error statuses:
- `Pending` (Scheduling or resource issue)
- `CrashLoopBackOff` (Application startup failure)
- `ImagePullBackOff` / `ErrImagePull` (Container image issue)
- `OOMKilled` (Container memory limit exceeded)

---

### Step 2: Describe the Pod and Check Events
The `describe` command provides container details, exit codes, and recent cluster events:
```bash
kubectl describe pod <pod-name> -n <namespace>
```
Scroll to the **Events** section at the bottom. This reveals 90% of operational issues (e.g., failed scheduling, probe failures, image pull failures, or mount errors).

---

### Step 3: Inspect Container Logs
If the container was created or attempted to run, examine the application logs:
```bash
# Check current logs
kubectl logs <pod-name> -n <namespace>

# If pod is restarting, inspect the previous crashed instance
kubectl logs <pod-name> -n <namespace> --previous

# If multi-container pod, specify the container
kubectl logs <pod-name> -c <container-name> -n <namespace>
```

---

### Step 4: Verify Configurations and Secrets
Confirm that required ConfigMaps, Secrets, and persistent volumes are present and correctly formatted:
```bash
kubectl get configmap -n <namespace>
kubectl get secret -n <namespace>
kubectl get pvc -n <namespace>
```

---

### Step 5: Verify Service Endpoints and Network Connectivity
If the pod is running but not receiving traffic:
```bash
# Check if Service has matching endpoints
kubectl get endpoints <service-name> -n <namespace>

# Verify labels match between Pod and Service selector
kubectl get service <service-name> -n <namespace> -o yaml | grep -A 5 selector
```

---

### Step 6: Interactive Debugging (If Pod is Running)
If the pod is running but misbehaving internally:
```bash
kubectl exec -it <pod-name> -n <namespace> -- /bin/sh
# Inside container: test localhost connectivity, verify environment variables, curl endpoints
```

<summary><strong>● Suppose you have a Kubernetes cluster with both node autoscaling and pod autoscaling enabled. After deploying a new release, the new pod replicas are unable to be scheduled on nodes, and node autoscaling is not triggering. What could be the possible root causes for this problem?</strong></summary>

**Answer:**
In Kubernetes, Horizontal Pod Autoscaler (HPA) increases pod replicas, and if worker nodes lack capacity, the new pods enter a `Pending` state. The **Cluster Autoscaler (CA)** or **Karpenter** observes these `Pending` pods and provisions new nodes.

If pods remain `Pending` and node autoscaling is **NOT** triggering, the root causes generally fall into the following categories:

---

### 1. Cluster Autoscaler Configuration & Limit Constraints
- **Max Nodes Limit Reached:** The Auto Scaling Group (ASG) or Cluster Autoscaler configuration has reached its maximum node limit (`--max-nodes` ceiling). Cluster Autoscaler will not launch nodes past this threshold.
- **Autoscaler Disabled / Not Running:** The Cluster Autoscaler pod in `kube-system` might be down, crashed, or starved of CPU/memory resources.
- **Missing Cloud Tags:** On AWS, the underlying EC2 Auto Scaling Group is missing required discovery tags:
  - `k8s.io/cluster-autoscaler/enabled`
  - `k8s.io/cluster-autoscaler/<cluster-name>`

---

### 2. Unfulfillable Pod Scheduling Constraints
If a pod has constraints that no available node or prospective node group can satisfy, the Cluster Autoscaler recognizes that adding new nodes will not help, so it does not scale:
- **NodeSelector / NodeAffinity Mismatch:** The new pod requires a label (e.g., `disktype: ssd` or `gpu: true`) that does not exist in any configured node group or launch template.
- **Unmatched Taints and Tolerations:** Node groups have taints (e.g., `dedicated=batch:NoSchedule`), but the new deployment lacks corresponding tolerations.
- **Topology Spread Constraints / Zone Restrictions:** Strict topology constraints or pod anti-affinity rules prevent scheduling on both current and new nodes in available zones.
- **HostPort Conflicts:** The pod explicitly binds to a `hostPort` (e.g., port `8080`), and since only one pod per node can bind that port, it restricts placement.

---

### 3. Resource Requests Exceed Node Group Capacity
- **Unrealistically Large Requests:** If the pod requests `cpu: 32` or `memory: 128Gi`, and the node group's instance type is `t3.xlarge` (4 vCPU, 16 GiB), no single node can ever fit the pod. The autoscaler skips scaling because the instance type is too small.

---

### 4. Cloud Provider & Infrastructure Bottlenecks
- **Cloud Provider Quota Exhaustion:** The AWS account has hit its EC2 vCPU service quota in the region.
- **Insufficient Cloud Capacity:** The cloud provider has run out of capacity for that specific EC2 instance type in that Availability Zone (`InsufficientInstanceCapacity`).
- **Subnet Private IP Exhaustion:** The VPC subnet has no available IP addresses left to assign to new EC2 instances or ENIs (AWS VPC CNI).
- **IAM Permission Failures:** The Cluster Autoscaler IAM Role (IRSA) lacks permissions to call `autoscaling:SetDesiredCapacity` or `ec2:DescribeLaunchTemplateVersions`.

---

### How to Diagnose:
1. Check pod events: `kubectl describe pod <pending-pod-name>` (look for `0/N nodes available` and autoscaler event notes).
2. Inspect Cluster Autoscaler logs:
   ```bash
   kubectl logs -n kube-system -l app=cluster-autoscaler --tail=100
   ```
   Look for messages such as `pod didn't trigger scale-up`, `max limit reached`, or `no node group matches pod requirements`.
</details>

<summary><strong>↳ Follow-up: You mentioned you used Helm charts for deploying that application. What was the purpose of using Helm instead of a normal Kubernetes deployment?</strong></summary>

**Answer:**
While standard Kubernetes YAML manifests work for simple applications, managing raw manifests across multiple environments quickly becomes repetitive and error-prone. **Helm** functions as the package manager for Kubernetes and provides significant operational advantages:

---

### Key Advantages of Helm Over Plain Kubernetes Manifests:

### 1. Dynamic Templating & Parameterization
- **Plain YAML:** Requires maintaining separate, duplicate YAML files for each environment (`dev-deployment.yaml`, `qa-deployment.yaml`, `prod-deployment.yaml`), leading to configuration drift.
- **Helm:** Uses a single set of template files and allows swapping values dynamically through `values-dev.yaml`, `values-qa.yaml`, and `values-prod.yaml`, or injecting parameters via CLI (`--set image.tag=1.2.0`).

### 2. Versioning & One-Command Rollbacks
- **Plain YAML:** If an update breaks multiple resources (Deployment, ConfigMap, Service), rolling back each component manually is tedious and risky.
- **Helm:** Tracks release history. With a single command:
  ```bash
  helm rollback <release-name> <revision-number>
  ```
  Helm atomically rolls back all associated resources to the previous working state.

### 3. Unified Release Lifecycle Management
- **Plain YAML:** An application consists of 5–10 resources (Deployment, Service, Ingress, HPA, ConfigMap, Secret, ServiceAccount). Applying or deleting them requires managing multiple files (`kubectl apply -f folder/`).
- **Helm:** Treats all related Kubernetes resources as a single unified package (release). Installing, upgrading, or deleting the entire stack is one command:
  ```bash
  helm install my-app ./my-chart
  helm upgrade my-app ./my-chart
  helm uninstall my-app
  ```

### 4. Dependency Management
- Helm allows defining application dependencies in `Chart.yaml` (e.g., a web service depending on Redis or PostgreSQL subcharts). Running `helm dependency update` automatically packages and installs dependencies together.

### 5. CI/CD Pipeline Efficiency
- Easily integrates into Jenkins, GitHub Actions, or Argo CD. Pipelines simply pass the latest Docker image tag and environment config to Helm during deployment.
</details>

<summary><strong>● If your AWS EC2 instance is running but the application hosted on it is not accessible, how would you troubleshoot the issue?</strong></summary>

**Answer:**
I follow a structured, step-by-step troubleshooting methodology moving from the external cloud network layer down to the operating system and application process:

---

### Step 1: Verify AWS Network & Security Settings (Cloud Layer)
1. **Security Group:** Verify that the inbound rules allow traffic on the application port (e.g., port 80, 443, or 8080) from your client IP, CIDR, or Load Balancer.
2. **Network ACLs:** Check the subnet's Network ACL to ensure both inbound and outbound traffic are allowed (NACLs are stateless and need outbound ephemeral ports 1024–65535 open).
3. **Route Table & Internet Gateway:** Ensure the public subnet route table has an explicit route `0.0.0.0/0 -> igw-xxxx`.
4. **Target Group Health (if behind ALB):** Check if the ALB Target Group shows the EC2 instance as `Healthy` or `Unhealthy`.

---

### Step 2: Test Server Accessibility (OS Access)
1. Connect to the instance using **AWS SSM Session Manager** or **SSH**.
2. If unreachable, check the **EC2 Status Checks** (System Status Check and Instance Status Check) in the AWS Console.

---

### Step 3: Check Application Service Status (Process Layer)
Once logged into the server:
1. Verify if the application service is running:
   ```bash
   sudo systemctl status <app-service-name>
   # Or for containers:
   docker ps -a
   ```
2. If stopped or in a failed state, inspect recent logs:
   ```bash
   sudo journalctl -u <app-service-name> -n 100 --no-pager
   # Or for container:
   docker logs --tail 100 <container-id>
   ```

---

### Step 4: Verify Port Listening & Interface Binding (Network Layer)
1. Check if the application is actively listening on the target port:
   ```bash
   sudo ss -tulnp | grep <port>
   # or
   sudo netstat -tulnp | grep <port>
   ```
2. **Critical Binding Check:** Verify that the application is bound to `0.0.0.0:<port>` (all interfaces) or the private IP, **NOT** `127.0.0.1:<port>` (localhost only). If bound only to `127.0.0.1`, external network packets cannot reach it.

---

### Step 5: Test Localhost Connectivity & OS Firewall
1. Test local connectivity from inside the instance:
   ```bash
   curl -v http://localhost:<port>
   ```
   - If local `curl` returns HTTP 200 OK, the application works fine locally—the issue is strictly at the network, Security Group, or OS firewall layer.
2. Check internal Linux firewall:
   ```bash
   sudo ufw status
   # or
   sudo iptables -L -n -v
   ```

---

### Step 6: Check Server Resource Saturation
Check if the instance has run out of memory or disk space:
```bash
top          # Check CPU and memory usage
free -m      # Check RAM and swap availability
df -h        # Check root and data disk capacity
```

**Answer:**

---

### Step 1: Identify Top CPU-Consuming Processes
1. **Interactive Monitoring:** Run `top` or `htop`. In `top`, press `Shift + P` to sort processes by CPU utilization in descending order.
2. **Instant Snapshot Command:**
   ```bash
   ps aux --sort=-%cpu | head -n 10
   ```
   This immediately reveals the Top 10 CPU-consuming processes with their PID, User, `%CPU`, `%MEM`, and full execution command.

---

### Step 2: Analyze CPU State Breakdown in `top`
Look at the `%Cpu(s)` header line in `top`:
- **`%us` (User CPU high):** Application code execution (e.g., infinite loops, heavy calculations, uncontrolled recursion, or high web traffic).
- **`%sy` (System CPU high):** Kernel overhead, system calls, or excessive context switching.
- **`%wa` (I/O Wait high):** CPU is waiting for disk read/write operations. Use `iostat -xz 1` to locate disk saturation bottlenecks.

---

### Step 3: Investigate the Specific Offending PID
1. **Inspect Individual Threads:**
   ```bash
   top -H -p <PID>
   ```
   This displays which specific threads inside the process are consuming the CPU.
2. **Inspect Open Files and Network Sockets:**
   ```bash
   sudo lsof -p <PID>
   sudo ss -tp | grep <PID>
   ```
3. **Review Application Logs:**
   Inspect the application's log files for repeated errors, endless retry loops, or massive transaction queries.

---

### Step 4: Remediation Actions
- **Immediate Recovery:**
  - Gracefully restart the service: `sudo systemctl restart <service-name>`
  - If hung, terminate the runaway process: `sudo kill -15 <PID>` (or `sudo kill -9 <PID>` as a last resort).
- **Long-Term Prevention:**
  - Scale vertically (upgrade to a larger EC2 instance type with more vCPUs).
  - Scale horizontally by adding the instance behind an Application Load Balancer inside an Auto Scaling Group (ASG).
  - Optimize application code, memory caching, and database queries.

**Answer:**
Metrics, logs, alarms, and dashboards represent the four fundamental pillars of monitoring and observability:

---

### 1. Metrics (Numerical Time-Series Data):
- **What it is:** Numeric values measured, recorded, and aggregated at regular time intervals.
- **Example:** CPU usage (78%), memory consumption (3.4 GB), incoming request rate (250 req/sec), disk write IOPS.
- **Primary Use:** Analyzing performance trends over time, capacity planning, and triggering automated scaling (HPA or ASG).

### 2. Logs (Descriptive Text Event Records):
- **What it is:** Detailed, timestamped textual records emitted by applications, operating systems, or infrastructure when events occur.
- **Example:** `[2026-11-02 19:15:20] ERROR: DB connection timeout on host 10.0.1.45:5432`.
- **Primary Use:** Root cause analysis (RCA), detailed debugging, understanding *why* an error occurred, and security audits.

---

### 3. Alarms (Automated Notification Triggers):
- **What it is:** Predefined rules and thresholds that continuously evaluate metrics or log filters.
- **Example:** "If CPU utilization exceeds 85% for more than 5 minutes, send an alert to PagerDuty."
- **Primary Use:** Proactive notification to wake up or alert engineers so incidents can be resolved before users notice degradation.

---

### 4. Dashboards (Visual Presentation Layer):
- **What it is:** Web-based graphical consoles that combine multiple metric charts, gauges, log streams, and alarm statuses into a single view.
- **Example:** A Grafana or CloudWatch dashboard showing EC2 CPU, RDS query latency, pod restart counts, and error rates side-by-side.
- **Primary Use:** Single-pane-of-glass operational visibility for DevOps teams and business stakeholders.

---

### 5. Summary Comparison Table:
| Component | Data Format | Core Question Answered | Primary Use Case |
| :--- | :--- | :--- | :--- |
| **Metrics** | Numeric numbers over time | *"Is the system healthy, and how is it performing?"* | Performance trending & autoscaling |
| **Logs** | Text records with timestamps | *"Why did a specific event or error happen?"* | Deep root cause analysis & debugging |
| **Alarms** | Boolean trigger conditions | *"When do engineers need to intervene?"* | Proactive incident alerting |
| **Dashboards** | Graphs, gauges, tables | *"What is the overall state of the platform right now?"* | High-level operational visibility |

<summary><strong>● What is the difference between AWS SQS Standard queues and FIFO queues?</strong></summary>

**Answer:**
Amazon SQS (Simple Queue Service) offers two types of message queues tailored for different architecture needs:

---

### 1. Standard Queues:
- **Message Ordering:** Best-effort ordering (messages are usually delivered in the order received, but occasional out-of-order delivery may occur).
- **Delivery Guarantee:** At-least-once delivery (every message is delivered at least once, but occasional duplicate copies can be delivered).
- **Throughput:** Nearly unlimited transactions per second (supports virtually unlimited message volume).
- **Naming:** Can use any valid queue name (e.g., `user-notifications`).
- **Ideal Use Case:** Asynchronous decoupled workloads where duplicate messages can be safely ignored (idempotent consumers) and order is not critical (e.g., sending email notifications, batch image processing).

---

### 2. FIFO Queues (First-In, First-Out):
- **Message Ordering:** Strict First-In, First-Out order preservation (messages are delivered in the exact order they are sent).
- **Delivery Guarantee:** Exactly-once delivery (duplicates are automatically eliminated via Message Deduplication ID).
- **Throughput:** Limited to 300 transactions per second (or up to 3,000 per second with message batching, or higher with high-throughput FIFO mode).
- **Naming:** Queue name must explicitly end with the `.fifo` suffix (e.g., `order-checkout.fifo`).
- **Ideal Use Case:** Critical transactional operations where order and deduplication are mandatory (e.g., bank deposits/withdrawals, e-commerce order processing, inventory seat booking).

---

### 3. Comparison Table:
| Feature | SQS Standard Queue | SQS FIFO Queue |
| :--- | :--- | :--- |
| **Ordering** | Best-effort (may arrive out of order) | Strictly First-In-First-Out (preserved) |
| **Delivery Guarantee** | At-least-once (duplicates possible) | Exactly-once (automatic deduplication) |
| **Throughput** | Nearly unlimited throughput | 300 TPS (up to 3,000 TPS with batching) |
| **Queue Name Format** | Any alphanumeric name | Must end with `.fifo` suffix |
| **Cost** | Slightly lower price per million requests | Slightly higher price per million requests |
</details>

<summary><strong>● If a Kubernetes pod is in CrashLoopBackOff state, how would you troubleshoot it?</strong></summary>

**Answer:**
A `CrashLoopBackOff` state indicates that a pod's container starts, fails or crashes, and Kubernetes attempts to restart it repeatedly with an exponentially increasing backoff delay (10s, 20s, 40s... up to 5 minutes).

---

### Step-by-Step Troubleshooting Workflow:

#### Step 1: Check Pod Status and Restart Count
```bash
kubectl get pods -n <namespace>
```
Note the restart count and current status of the pod.

#### Step 2: Inspect Pod Events and Container Exit Code
```bash
kubectl describe pod <pod-name> -n <namespace>
```
Look closely at the `Last State` section for the **Exit Code**:
- **Exit Code 0:** The container executed its process and exited normally (often occurs if the container runs a command that completes and has no long-running foreground daemon).
- **Exit Code 1 / 2:** Application error (uncaught exception, missing configuration, syntax error).
- **Exit Code 137 (OOMKilled):** The container exceeded its memory limit (`resources.limits.memory`) and was killed by the Linux kernel Out-Of-Memory killer.
- **Exit Code 139:** Segmentation fault in the application code.

#### Step 3: Inspect Container Logs
1. View current container logs:
   ```bash
   kubectl logs <pod-name> -n <namespace>
   ```
2. **Crucial Diagnostic Step:** If the pod has crashed and restarted, view the logs from the *previous crashed instance*:
   ```bash
   kubectl logs <pod-name> --previous -n <namespace>
   ```
   *(If the pod has multiple containers, specify the container with `-c <container-name>`)*.

#### Step 4: Verify Configuration & Dependencies
Check for common configuration issues:
- **Missing Environment Variables / Secrets:** Check if ConfigMaps or Secrets referenced by the pod exist and have the correct keys.
- **Database / Network Connectivity:** Ensure the application can reach required downstream services (e.g., RDS PostgreSQL, Redis) during its startup routine.
- **Aggressive Liveness Probe:** If the `initialDelaySeconds` is too low, Kubernetes may kill the container before it finishes initializing.

#### Step 5: Interactive Debugging (if needed)
If the container crashes too quickly to view logs:
- Temporarily modify the pod manifest's `command` to `["sleep", "3600"]` to keep the container running.
- Exec into the container to inspect environment variables and files:
  ```bash
  kubectl exec -it <pod-name> -n <namespace> -- /bin/sh
  ```

<summary><strong>● If a Kubernetes pod is stuck in Pending state, what are the possible reasons?</strong></summary>

**Answer:**
A `Pending` state means the pod manifest has been accepted by the Kubernetes API server, but one or more of its containers have not been scheduled onto a worker node.

---

### Primary Reasons for Pending Pods:

1. **Insufficient Node Resources (CPU or Memory):**
   - The worker nodes do not have enough unallocated CPU or Memory to satisfy the pod's `resources.requests`.
   - *Diagnostic:* Run `kubectl describe pod <pod-name>` -> look at the **Events** section for:
     `0/N nodes available: Insufficient cpu, Insufficient memory`.
2. **Node Taints and Tolerations:**
   - Worker nodes have taints applied (e.g., `workload=gpu:NoSchedule`), and the pod manifest lacks the matching tolerations.
3. **NodeSelector or Node Affinity Restrictions:**
   - The pod specifies a `nodeSelector` or `nodeAffinity` label (e.g., `topology.kubernetes.io/zone=us-east-1a` or `hardware=high-memory`) that matches zero available nodes.
4. **PersistentVolumeClaim (PVC) Issues:**
   - The pod requests a PersistentVolumeClaim that is in `Pending` state, or the associated StorageClass cannot dynamically provision the storage volume, or an AWS EBS volume cannot attach because the node is in a different Availability Zone.
5. **Missing ConfigMap or Secret:**
   - The pod manifest references a ConfigMap or Secret that does not exist and is marked mandatory (`optional: false`).
6. **Autoscaler Scaling Delay:**
   - The cluster has exhausted capacity and the Cluster Autoscaler / Karpenter is actively launching new EC2 worker nodes. The pod remains in `Pending` until the new node registers as `Ready`.
</details>

<details>
<summary><strong>● What is the difference between liveness, readiness, and startup probes in Kubernetes?</strong></summary>

**Answer:**
Kubernetes uses three distinct health probes to manage container lifecycle and traffic routing:

---

### 1. Startup Probe:
- **Purpose:** Determines whether the application process inside the container has completed its initial boot sequence.
- **Behavior:** **Disables both liveness and readiness checks** until the startup probe succeeds. This prevents slow-starting applications (e.g., Java/Spring Boot apps that take 60–90 seconds to initialize) from being prematurely terminated by liveness probes.
- **Action on Failure:** Kubelet kills the container and restarts it according to the pod's `restartPolicy`.

---

### 2. Readiness Probe:
- **Purpose:** Determines whether the container is ready to accept and serve user network traffic.
- **Behavior:** Checks if the application is fully prepared to handle requests (e.g., database connections are established, warm-up caches are loaded).
- **Action on Failure:** The pod's IP address is **removed from the Kubernetes Service endpoints**. **The container is NOT killed or restarted.** User traffic is stopped until the probe passes again.

---

### 3. Liveness Probe:
- **Purpose:** Determines whether the container is still running and healthy (deadlock and freeze detection).
- **Behavior:** Continuously checks if the application has entered a broken state (such as a thread deadlock or memory leak) where it cannot recover on its own.
- **Action on Failure:** Kubelet **kills the container and restarts it**.

---

### 4. Comparison Summary Table:
| Probe Type | What It Checks | Action Taken on Failure | Typical Failure Scenario |
| :--- | :--- | :--- | :--- |
| **Startup Probe** | Has the container completed initial booting? | Kills and restarts the container | Slow application initialization |
| **Readiness Probe** | Can the container handle user traffic right now? | Removes pod IP from Service endpoints (no restart) | Cache warming, temporary DB disconnect, overload |
| **Liveness Probe** | Is the application alive and functional? | Kills and restarts the container | Deadlock, infinite loop, frozen process |
</details>

<summary><strong>● What is the difference between a Docker image and a Docker container?</strong></summary>

**Answer:**
A Docker image and a Docker container represent two different states of application packaging and runtime:

---

### 1. Simple Analogy:
- A **Docker Image** is like a **Blueprint** or a **Recipe**.
- A **Docker Container** is the **Actual House built from the blueprint** or the **Cake baked from the recipe**.
- In Object-Oriented Programming: An Image is the **Class**, while a Container is an instantiated **Object**.

---

### 2. Docker Image:
- **Definition:** A read-only, immutable template consisting of stacked layers containing the application source code, runtime, system libraries, and default environment variables.
- **Characteristics:** Static; does not run or consume active CPU/memory; stored on disk or in remote registries (Docker Hub, Amazon ECR).
- **Creation:** Built from a `Dockerfile` using `docker build`.

---

### 3. Docker Container:
- **Definition:** A runnable, isolated runtime instance created from a Docker image.
- **Characteristics:** Dynamic; executes active processes; adds a thin, writable container layer on top of the immutable image layers; consumes host CPU, memory, and networking.
- **Creation:** Created and started from an image using `docker run` or `docker create`.

---

### 4. Comparison Table:
| Feature | Docker Image | Docker Container |
| :--- | :--- | :--- |
| **State** | Static (read-only snapshot) | Dynamic (live running/stopped instance) |
| **Storage Layer** | Immutable stacked read-only layers | Read-only layers + top writable layer |
| **Resource Usage** | Consumes disk space only | Consumes CPU, RAM, disk, and network |
| **Lifecycle** | Built (`docker build`), tagged, pushed | Created, Started, Stopped, Restarted, Deleted |
| **Quantity** | One image | Can spawn multiple identical containers from one image |
</details>

<summary><strong>● If a Grafana dashboard shows no data, how would you troubleshoot it?</strong></summary>

**Answer:**
When a Grafana dashboard displays "No Data", I follow this systematic troubleshooting workflow:

---

### Step 1: Check the Selected Time Range & Dashboard Variables
1. **Time Range:** Verify the time range in the upper-right corner. If set to a narrow window (e.g., "Last 5 minutes") and the service was idle or metrics scrape interval is large, it may display no data. Test by expanding to "Last 1 hour" or "Last 24 hours".
2. **Dashboard Variables:** Check the dropdown filter variables (Cluster, Namespace, Job, Node). Ensure an active, valid value is selected rather than a decommissioned or deleted resource.

---

### Step 2: Use the Panel Query Inspector
1. Click the panel title -> click **Edit** -> click **Query Inspector**.
2. Click **Refresh** to inspect the raw query and JSON response:
   - If response returns `[]` (empty array), the query syntax or metric name is likely incorrect.
   - If response returns an HTTP 4xx or 5xx error, check the specific error message returned by the data source.

---

### Step 3: Test the Data Source Connection
1. Navigate to **Administration -> Connections -> Data Sources** -> select the data source (e.g., Prometheus).
2. Click **"Save & Test"**:
   - If it fails (e.g., "HTTP Error Bad Gateway" or "Connection Refused"):
     - Verify the backend URL (e.g., `http://prometheus-server:9090` or `http://prometheus-k8s.monitoring.svc:9090`).
     - Check network connectivity, DNS resolution, and firewall/Security Group rules between Grafana and the data source.

---

### Step 4: Validate Metrics Directly in the Monitoring Backend
1. Open the Prometheus Web UI directly and execute the exact PromQL query:
   - If Prometheus returns results, the issue is strictly within Grafana's panel configuration or PromQL expression.
   - If Prometheus also returns no data, the problem is at the metric scrape/collection layer.

---

### Step 5: Check Scrape Targets and Exporters
1. In the Prometheus Web UI, navigate to **Status -> Targets**:
   - Check if the relevant scrape target (e.g., `node-exporter`, `kube-state-metrics`, application pods) is in `UP` (green) or `DOWN` (red) state.
2. If `DOWN`, inspect the exporter pod logs:
   ```bash
   kubectl logs -l app=node-exporter -n monitoring
   ```

<details>
<summary><strong>● In bash or shell on Linux, how would you list files modified within a specific date range, for example from January 2025 to December 2025?</strong></summary>

**Answer:**
There are multiple ways to list files modified within a specific date range in Linux:

---

### Method 1: Using `find` with `-newermt` (Recommended & Most Direct)
The `find` command provides the `-newermt` flag to specify human-readable modification timestamps:

```bash
find /path/to/search -type f -newermt "2025-01-01" ! -newermt "2025-12-31 23:59:59"
```

#### Explanation:
- `-type f`: Searches only for regular files (excluding directories).
- `-newermt "2025-01-01"`: Matches files modified on or after January 1, 2025 at 00:00:00.
- `! -newermt "2025-12-31 23:59:59"`: Negation operator (`!`) excludes files modified after December 31, 2025 at 23:59:59.

#### To display detailed file information (permissions, size, modification date):
```bash
find /path/to/search -type f -newermt "2025-01-01" ! -newermt "2025-12-31 23:59:59" -exec ls -lh {} +
```

---

### Method 2: Using Reference Files with `touch -t` (Compatible with Older Systems)
If `-newermt` is unavailable on older Unix/Linux distributions, create temporary boundary files:

```bash
# 1. Create boundary timestamp reference files
touch -t 202501010000 /tmp/start_boundary
touch -t 202512312359 /tmp/end_boundary

# 2. Find files modified between the two boundary files
find /path/to/search -type f -newer /tmp/start_boundary ! -newer /tmp/end_boundary

# 3. Clean up boundary files
rm -f /tmp/start_boundary /tmp/end_boundary
```

---

### Method 3: Using `ls` with `awk` (For Single Directory Inspection)
To quickly check files in a single directory without searching recursively:

```bash
ls -l --time-style=+"%Y-%m-%d" /path/to/search | awk '$6 >= "2025-01-01" && $6 <= "2025-12-31" {print $6, $7}'
```
</details>

<summary><strong>● If a production application running on Kubernetes suddenly experiences a 10x increase in latency or traffic, what would be your approach to investigate and resolve the problem?</strong></summary>

**Answer:**
I approach sudden traffic or latency spikes using a three-phase incident response methodology: **Immediate Mitigation -> Bottleneck Diagnosis -> Long-Term Hardening**.

---

### Phase 1: Immediate Stabilization (First 2–5 Minutes)
1. **Emergency Horizontal Pod Scaling:**
   - If the Horizontal Pod Autoscaler (HPA) is slow to respond, manually scale up pod replicas immediately to distribute the load:
     ```bash
     kubectl scale deployment <app-name> --replicas=<higher-count> -n <namespace>
     ```
2. **Verify Cluster Node Capacity:**
   - Check if worker nodes have sufficient compute to host new pods:
     ```bash
     kubectl top nodes
     ```
   - If nodes are saturated, ensure Karpenter or Cluster Autoscaler is spinning up new worker nodes.
3. **Filter Malicious / Runaway Traffic:**
   - Check whether the spike is legitimate organic traffic or a DDoS attack / runaway bot scraper.
   - If abusive, enable rate limiting, geo-blocking, or AWS WAF rules at the CloudFront / Application Load Balancer level.

---

### Phase 2: Bottleneck Diagnosis (Deep Investigation)
1. **Check Pod CPU/Memory Throttling:**
   - Run `kubectl top pods -n <namespace>` to check if pods are hitting CPU limits. Heavy CPU throttling causes severe request queuing and latency spikes.
2. **Check Downstream Databases & Caches:**
   - High traffic usually pushes the bottleneck down to relational databases:
     - Check Amazon RDS CPU utilization, active database connections, and slow query logs.
     - Check Redis cache hit/miss ratio. If cache is missing, database reads spike exponentially.
     - Increase database connection pool size or add RDS Read Replicas if read contention is high.
3. **Inspect Ingress & Application Latencies:**
   - Check Ingress / ALB metrics (`TargetResponseTime` and `HTTPCode_Target_5XX_Count`).
   - Use distributed tracing (Jaeger, Datadog, or AWS X-Ray) to locate the exact microservice span or external API call introducing the delay.

---

### Phase 3: Post-Incident Resolution & Hardening
- **Tune Autoscaling Policies:** Adjust HPA configuration to scale up faster (reduce `scaleUp.stabilizationWindowSeconds` to 0).
- **Implement Caching & Rate Limiting:** Add caching layers (Redis/ElastiCache) for frequent database queries and enforce client rate limiting.
- **Review Resource Requests/Limits:** Right-size container `requests` and `limits` to prevent CPU throttling under peak loads.
</details>

<summary><strong>● If you receive multiple critical alerts at the same time, how would you prioritize them?</strong></summary>

**Answer:**
When multiple critical alerts trigger simultaneously, I prioritize them using a structured triage framework based on **customer business impact**, **root cause identification**, and **team communication**:

---

### 1. Prioritize by Customer & Business Impact (Severity Triage):
- **Tier 1 (Highest Priority - Production Outage / Revenue Impact):**
  - Alerts directly causing customer-facing downtime, transaction failures, or data loss (e.g., *"Production Payment API returning 500 errors"*, *"E-commerce checkout down"*, *"Primary RDS database inaccessible"*).
- **Tier 2 (High Priority - Redundancy Loss / Degraded Performance):**
  - Alerts where redundancy has failed, but customer traffic is still functioning (e.g., *"RDS Multi-AZ Failover in progress"*, *"Kubernetes worker node NotReady"*, *"2 of 6 pods crashing in payment service"*).
- **Tier 3 (Medium Priority - Impending Thresholds):**
  - Alerts warning of impending exhaustion that have not yet impacted active users (e.g., *"EBS volume at 85% capacity"*, *"SSL certificate expiring in 5 days"*, *"Non-production batch job delayed"*).

---

### 2. Identify Root Cause vs Cascading Symptoms:
- A single upstream failure (such as an AWS NAT Gateway outage or an RDS database crash) can trigger 20+ downstream alerts across various microservices (e.g., Pod CrashLoopBackOff, API timeout alerts, SQS queue depth alerts).
- **Action:** Group alerts by timestamp and infrastructure dependency. Focus diagnosis immediately on the **shared upstream dependency** (Network -> Core Database -> Auth Service) rather than getting distracted by 20 individual microservice alerts.

---

### 3. Communicate and Mobilize (ChatOps):
- **Acknowledge Alerts:** Mark alerts as "Acknowledged" in PagerDuty / Opsgenie so the wider team knows the incident is actively owned.
- **Divide and Conquer:** If multiple genuinely independent critical issues occur, delegate secondary alerts to other on-call engineers.
- **Incident Communication:** Open an incident response bridge/Slack war room and post concise status updates every 15–30 minutes until resolution.
</details>
