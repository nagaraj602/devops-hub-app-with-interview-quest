<summary><strong>● Scenario: An API that has been working fine for 3 months (with no recent code deployment) suddenly starts responding 5 times slower than usual, and a customer reports timeout issues. What would be your mechanism/approach to triage this latency issue?</strong></summary>

**Answer:**
When an API that hasn't changed in months suddenly slows down, the root cause is almost always related to **data growth, downstream dependencies, traffic shifts, or resource exhaustion**. Here is my systematic triage process:

---

### Step 1: Check Traffic & Request Volume (Golden Signals)
- Check Grafana / CloudWatch to see if incoming request traffic (RPS) has spiked due to a marketing event, heavy customer batch upload, or a DDoS/bot attack.

---

### Step 2: Check Downstream Dependencies (The #1 Cause)
- **Database:** Over 3 months, table sizes grow significantly. A query that ran fast on 10,000 rows might do full table scans on 2,000,000 rows without proper indexing. Check RDS CPU, read/write IOPS, and run Amazon RDS Performance Insights to identify top slow SQL queries.
- **Cache:** Check Redis/Memcached hit ratio. If the cache expired, evicted keys, or crashed, all requests fall directly onto the database.
- **Third-Party APIs:** Check if the API calls external services (payment gateways, authentication providers, webhook endpoints) that might be experiencing degraded performance.

---

### Step 3: Check Pod & Node Resource Saturation
- Inspect CPU and memory usage (`kubectl top pods`, `kubectl top nodes`).
- Check if pods are experiencing CPU throttling (hitting `limits.cpu`) or spending excess time in JVM Garbage Collection.

---

### Step 4: Check Network & Load Balancer
- Check AWS ALB target response time and target health metrics to ensure traffic is evenly distributed across all availability zones.

---

### Immediate Mitigation:
- **If resource-bound:** Manually scale pod replicas (`kubectl scale deployment <name> --replicas=N`) or scale RDS read replicas.
- **If rogue client/bot:** Rate limit or block the abusive IP via AWS WAF or ALB rules.
- **If database query:** Advise database administrator / developers to add missing indexes or optimize the query.
</details>

#### 【 MONITORING 】

<details>
<summary><strong>↳ Follow-up: When latency issues occur, do you still check CPU and memory utilization as part of your troubleshooting?</strong></summary>

**Answer:**
**Yes, absolutely.** Checking CPU and memory utilization is one of the very first sanity checks I perform.

---

### Why It Is Essential:
1. **CPU Throttling:** In Kubernetes, if a container exceeds its configured CPU limit (`resources.limits.cpu`), the Linux kernel CFS (Completely Fair Scheduler) throttles the container's CPU shares. The container does not crash, but its execution speed drops drastically, causing direct 5x to 10x latency spikes.
2. **Memory Saturation & GC Pauses:** When memory approaches the container limit, runtimes like Java (JVM) or Node.js spend excessive CPU cycles running aggressive Garbage Collection (GC) pauses to free memory. During these 'stop-the-world' pauses, the application cannot process requests, leading to timeouts.
3. **Worker Node Saturation:** If the underlying Kubernetes EC2 node has high CPU or memory saturation from neighboring pods ('noisy neighbor' effect), all workloads on that node will experience degraded responsiveness.

*Running `kubectl top pods` and `kubectl top nodes` takes only a few seconds and immediately confirms or rules out resource starvation.*
</details>

#### 【 AWS / CLOUD 】

<details>
<summary><strong>↳ Follow-up: Given that AWS is designed to auto-scale resources on demand to prevent latency issues, why do you think engineers still need to check CPU and memory utilization when diagnosing latency problems in the cloud?</strong></summary>

**Answer:**
Autoscaling in AWS is a powerful feature, but it does **not** guarantee an application will never experience CPU or memory-induced latency. Here is why engineers must still check utilization:

1. **Autoscaling Takes Time (Warm-up Delay):** Autoscaling is reactive, not instantaneous. Detecting high load (30-60 seconds) plus spinning up a new EC2 worker node via Karpenter/Cluster Autoscaler (1-2 minutes) and pulling the Docker image takes 2 to 4 minutes. During that period, existing pods run at 100% capacity and user requests time out.
2. **Autoscaling Has Hard Ceilings:** Every Auto Scaling Group (ASG) and Horizontal Pod Autoscaler (HPA) has configured minimum and maximum limits (e.g., `maxReplicas: 10`). Once the max limit is hit, autoscaling stops, and pods saturate.
3. **Improper Scaling Metrics or Thresholds:** If the HPA is configured to trigger on 80% CPU utilization, but the application begins dropping connections or experiencing thread locking at 70%, autoscaling will never trigger.
4. **Non-Scalable Components:** While frontend and API pods can scale horizontally, backend databases (such as a single primary Amazon RDS instance) do not automatically scale horizontally without manual intervention or read replica configuration.
5. **Memory Leaks Cannot Be Solved by Autoscaling:** If an application leaks memory, launching more pods simply causes new pods to also run out of memory, multiplying the issue and driving up cloud costs.
</details>

<details>
<summary><strong>↳ Follow-up: If the same on-premises-style triaging steps (checking CPU/memory capacity) are used in a cloud environment, doesn't that defeat the purpose of being in the cloud? Why would someone still check capacity/utilization when the application is hosted in the cloud?</strong></summary>

**Answer:**
No, it does not defeat the purpose of being in the cloud. The key distinction is between **infrastructure agility** and **software resource consumption**:

---

### What the Cloud Actually Provides:
- The cloud provides **elasticity and programmable provisioning**—eliminating the weeks or months needed on-premises to purchase hardware, rack servers, and configure physical networking. You can scale from 2 servers to 50 servers in minutes via code.

---

### Why We Still Check Capacity in the Cloud:
1. **Software Physics Don't Change:** Whether code runs on an on-prem blade server or an AWS EC2 virtual machine, it still consumes physical CPU cycles, RAM, and network bandwidth. An inefficient algorithm or deadlocked thread will saturate resources in any environment.
2. **Cost Governance & Financial Safety:** In the cloud, infinite scaling means infinite billing. Autoscaling must be bounded by budget limits to prevent accidental cloud spend spikes.
3. **Identifying Root Cause vs Symptom:** Checking resource capacity helps diagnose *why* a problem occurred. If CPU is high because of legitimate traffic, you scale up (cloud solution). If CPU is high because of an infinite loop in code, scaling up simply burns money without fixing the bug (application defect).
4. **Architecture Constraints:** Components like stateful relational databases and distributed locks have vertical limits regardless of where they are hosted.
</details>

  ```bash
  kubectl describe pod <pod-name> -n <namespace> | grep -E "Terminated|Exit Code|OOMKilled"
  ```

  If the service is customer-impacting, temporarily patch the deployment memory limit:
  ```bash
  kubectl set resources deployment/<deployment-name> -n <namespace> --limits=memory=2Gi
  ```

  ```bash
  kubectl rollout restart deployment/<deployment-name> -n <namespace>
  ```

To deploy a Python backend and React frontend on AWS Kubernetes (EKS) and deliver a secure, production-grade URL, I consider five key architectural pillars:

---

### 1. Containerization & Dockerfile Strategy:
- **React Frontend:** Use a **multi-stage Docker build**. Stage 1 builds static assets using `node:alpine` (`npm run build`). Stage 2 copies the compiled static build to a lightweight `nginx:alpine` image to serve files efficiently with low memory footprint (~20MB).
- **Python Backend:** Use a slim base image (`python:3.11-slim`), run with a production WSGI/ASGI server like **Gunicorn / Uvicorn**, create a non-root application user, and optimize Docker layer caching for `requirements.txt`.
- Build and push images to **Amazon ECR** with semantic version tags and automated vulnerability scanning (Trivy).

---

### 2. Kubernetes Workload Manifests:
- Create separate `Deployment` manifests for frontend and backend with `replicas: 2` (minimum for high availability across AZs).
- Configure explicit **resource requests and limits** (CPU and memory) to prevent node starvation.
- Configure **Liveness and Readiness Probes** (e.g., `/healthz` endpoint on Python and HTTP 200 on Nginx).
- Store configuration in `ConfigMaps` and sensitive credentials (DB passwords, API keys) in `Secrets` (integrated with AWS Secrets Manager via External Secrets Operator).

---

### 3. Networking, Routing & Providing the URL:
- Define `ClusterIP` services for both frontend and backend.
- Deploy the **AWS Load Balancer Controller** in the EKS cluster.
- Create an **Ingress** resource that provisions an **Application Load Balancer (ALB)** with path-based routing:
  - Route `/api/*` to the Python backend service.
  - Route `/*` to the React frontend service.
- In **Amazon Route 53**, create a DNS `A` (Alias) or `CNAME` record pointing your domain (e.g., `app.mycompany.com`) to the ALB DNS name.
- Attach an **SSL/TLS certificate** from **AWS Certificate Manager (ACM)** to the ALB Ingress for HTTPS on port 443 with automated HTTP-to-HTTPS redirection.

---

### 4. High Availability & Scaling:
- Configure **Horizontal Pod Autoscaler (HPA)** to autoscale pods between 2 and 10 replicas based on 70% CPU/memory utilization.
- Use `topologySpreadConstraints` or pod anti-affinity to ensure replicas run across different Availability Zones.

---

### 5. CI/CD & Observability:
- Build a Jenkins pipeline to automate linting, testing, Docker image building, ECR push, and Helm deployment.
- Expose Prometheus `/metrics` on the backend and configure Grafana dashboards for monitoring.
</details>

<summary><strong>↳ Follow-up: Have you personally ever created new monitors/alerts in Prometheus for a new application?</strong></summary>

**Answer:**
Yes, I have created multiple custom Prometheus alerting rules using `PrometheusRule` CRDs. Here are three specific examples:

---

### 1. High HTTP 5xx Error Rate Alert (SRE Availability SLO):
Alerts when 5xx errors exceed 2% of total traffic over a 5-minute rolling window:
```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: api-5xx-error-alert
  namespace: monitoring
spec:
  groups:
  - name: api.rules
    rules:
    - alert: HighHttp5xxErrorRate
      expr: |
        (sum(rate(http_requests_total{status=~"5.."}[5m])) by (service)
        /
        sum(rate(http_requests_total[5m])) by (service)) * 100 > 2
      for: 3m
      labels:
        severity: critical
      annotations:
        summary: "High HTTP 5xx error rate on {{ $labels.service }}"
        description: "Service {{ $labels.service }} has a 5xx error rate of {{ $value }}%."
```

---

### 2. Pod Approaching Memory Limit Alert (Early OOM Prevention):
Fires before an OOMKill occurs when container memory exceeds 85% of its configured limit:
```yaml
    - alert: PodMemorySaturation
      expr: |
        (sum(container_memory_working_set_bytes{container!=""}) by (pod, namespace)
        /
        sum(kube_pod_container_resource_limits{resource="memory"}) by (pod, namespace)) * 100 > 85
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.pod }} memory utilization > 85%"
```

---

### 3. Frequent Pod Restart Alert:
Detects intermittent crash loops:
```yaml
    - alert: PodFrequentRestarts
      expr: increase(kube_pod_container_status_restarts_total[15m]) > 3
      for: 1m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ $labels.pod }} restarted {{ $value }} times in last 15 minutes."
```

<summary><strong>↳ Follow-up: What architecture or approach does your team follow in Terraform to avoid code repetition when deploying across dev, UAT, and production environments?</strong></summary>

**Answer:**
To avoid code duplication and enforce consistency across environments, we follow a **Modular Directory Architecture with Environment-Specific Inputs**:

---

### 1. Architecture Structure:
```text
terraform-repo/
├── modules/                  # Reusable, environment-agnostic modules
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── eks/
│   └── rds/
└── environments/             # Environment-specific caller configurations
    ├── dev/
    │   ├── main.tf           # Calls ../../modules/*
    │   ├── backend.tf        # Points to dev/terraform.tfstate in S3
    │   └── terraform.tfvars  # Small instances (t3.medium), single NAT gateway
    ├── uat/
    │   ├── main.tf
    │   ├── backend.tf        # Points to uat/terraform.tfstate in S3
    │   └── terraform.tfvars  # Medium sizing
    └── prod/
        ├── main.tf
        ├── backend.tf        # Points to prod/terraform.tfstate in S3
        └── terraform.tfvars  # Large instances (m5.xlarge), multi-AZ NAT, Multi-AZ RDS
```

---

### 2. Key Benefits of This Architecture:
- **Zero Code Duplication:** The underlying resource definitions (VPC, subnets, EKS, RDS) are written once in `modules/`. Each environment directory simply invokes the module and provides variable values.
- **Strict State Isolation:** Each environment uses an independent S3 backend key (`key = "dev/terraform.tfstate"` vs `"prod/terraform.tfstate"`). A state file corruption or destructive change in Dev can never affect Production.
- **Configurable Environment Sizing:** Dev uses 1 NAT Gateway and spot instances to save cost, while Prod uses 3 NAT Gateways across 3 AZs and on-demand instances.

*(Alternative Mention: We also evaluated **Terraform Workspaces**, but preferred directory-based separation for production workloads because it provides physical backend isolation and simpler RBAC access control).*
</details>

#### 【 CI/CD 】

<details>
<summary><strong>↳ Follow-up: How does your CI/CD pipeline (e.g., Jenkins or GitLab) determine which environment to deploy to, ensuring it doesn't accidentally deploy to production?</strong></summary>

**Answer:**
We implement a multi-layered guardrail mechanism in our CI/CD pipelines to ensure deployments target the correct environment and cannot accidentally deploy to production:

---

### 1. Git Branch-to-Environment Mapping (GitFlow):
Our declarative Jenkins pipeline inspects the Git branch or tag that triggered the build:
- **`develop` branch:** Automatically builds, tests, and deploys to **Development**.
- **`release/*` branch or PR merge to `staging`:** Deploys to **UAT / Staging**.
- **Git Tag on `main` branch (e.g., `v1.2.0`):** Only tagged release commits on `main` are eligible for **Production**.

---

### 2. Jenkins Declarative Pipeline Guardrails (`when` directives):
```groovy
stage('Deploy to Production') {
    when {
        buildingTag()
        branch 'main'
    }
    steps {
        // Production deployment steps
    }
}
```

---

### 3. Mandatory Manual Approval Gate:
Even when code is tagged on `main`, the production stage is paused behind an interactive approval gate:
```groovy
stage('Production Approval Gate') {
    steps {
        timeout(time: 2, unit: 'HOURS') {
            input message: "Approve deployment of version ${TAG_NAME} to Production?",
                  submitter: 'lead-devops,release-manager'
        }
    }
}
```
Only authorized team leads have Jenkins RBAC permissions to click 'Approve'.

---

### 4. Isolated Credentials & Secrets:
Production AWS IAM credentials and Kubernetes kubeconfig files are isolated in Jenkins credentials store and restricted strictly to production job stages. Development and UAT pipeline runs physically lack the credentials needed to interact with the production cluster.

---

### 5. Automated Post-Deployment Smoke Tests & Rollback:
Immediately following deployment, automated health checks verify the readiness of new pods. If health checks fail or error rates increase, the pipeline triggers an immediate automated `helm rollback`.
