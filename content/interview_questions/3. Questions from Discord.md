### The Complete 6-Step Incident Lifecycle:

```text
[1. Detection & Alert] ➔ [2. Acknowledge & Triage] ➔ [3. Immediate Containment] ➔ [4. Deep Investigation / RCA] ➔ [5. Permanent Fix] ➔ [6. Closure & Post-Mortem]
```

1. **Step 1: Detection & Alert Trigger:**
   - Prometheus Alertmanager or CloudWatch detects an anomaly (e.g., API 5xx error rate spikes above 2% for 3 minutes).
   - An incident is automatically created in PagerDuty, triggering push notifications and phone calls to the on-call engineer.
2. **Step 2: Acknowledgement & Triage (Within SLA):**
   - The on-call engineer acknowledges the alert in PagerDuty via mobile app or Slack within 5–15 minutes, stopping the automated escalation policy.
   - An incident bridge (Slack channel / Zoom call) is opened for team visibility.
3. **Step 3: Immediate Mitigation & Containment (Stop the Bleeding):**
   - The primary goal is restoring customer service immediately rather than debugging the full code:
     - **Option A (Recent Deployment Issue):** Initiate an instant rollback using `helm rollback <release> <revision>` or Git revert.
     - **Option B (Traffic Spike):** Scale up replicas immediately (`kubectl scale deployment ... --replicas=N`) or scale up worker node capacity.
     - **Option C (Downstream Dependency Failure):** Enable circuit breakers or route traffic to a maintenance fallback page.
4. **Step 4: Investigation & Root Cause Analysis (RCA):**
   - Once metrics stabilize, investigate the root cause:
     - Check distributed logs in Kibana or CloudWatch Logs Insights by filtering on transaction IDs and HTTP status 500.
     - Inspect Kubernetes events (`kubectl describe pod`) to verify pod exit codes or memory pressure.
     - Correlate with recent code commits or cloud configuration changes in CloudTrail.
5. **Step 5: Permanent Resolution & Verification:**
   - Developers write a bug fix or configuration patch.
   - The fix is verified in Staging, approved, and deployed through the standard CI/CD pipeline to Production.
   - Monitor Grafana dashboards for 15–30 minutes to ensure error rates remain at 0%.
6. **Step 6: Incident Closure & Blameless Post-Mortem:**
   - Resolve and close the incident in PagerDuty and Jira.
   - Conduct a blameless post-mortem meeting to review what happened, why it happened, and create preventive Jira tickets (e.g., add new alerts, improve test coverage, right-size memory).

CURRENT_USAGE=$(df / | grep / | awk '{ print $5 }' | sed 's/%//g')

    find /var/log/apps -type f -name "*.log" -mtime +7 -exec gzip {} \;

    find /var/log/apps -type f -name "*.gz" -mtime +30 -exec rm -f {} \;

### Example 2: SSL/TLS Certificate Expiration Monitoring
Checks endpoint certificate expiration and sends an automated webhook alert to Slack if renewal is needed:
```bash
#!/bin/bash
DOMAIN="api.company.com"
EXPIRY_DATE=$(openssl s_client -servername "$DOMAIN" -connect "$DOMAIN:443" </dev/null 2>/dev/null | openssl x509 -noout -enddate | cut -d= -f2)
EXPIRY_EPOCH=$(date -d "$EXPIRY_DATE" +%s)
NOW_EPOCH=$(date +%s)
DAYS_LEFT=$(( ($EXPIRY_EPOCH - $NOW_EPOCH) / 86400 ))

if [ "$DAYS_LEFT" -lt 15 ]; then
    curl -X POST -H 'Content-type: application/json' \
      --data "{\"text\":\"⚠️ SSL Warning: Certificate for $DOMAIN expires in $DAYS_LEFT days!\"}" \
      "$SLACK_WEBHOOK_URL"
fi
```

### Example 3: Automated Database Backup & S3 Encryption Upload

#!/bin/bash
DATE=$(date +%Y-%m-%d_%H%M%S)
BACKUP_DIR="/tmp/db_backups"
mkdir -p "$BACKUP_DIR"

PGPASSWORD="$DB_PASSWORD" pg_dump -h "$DB_HOST" -U "$DB_USER" "$DB_NAME" | gzip > "$BACKUP_DIR/backup_$DATE.sql.gz"

rm -f "$BACKUP_DIR/backup_$DATE.sql.gz"

<summary><strong>● Suppose you deploy an application and immediately afterward it starts returning HTTP 403 errors. How would you investigate and troubleshoot this issue?</strong></summary>

**Answer:**
An **HTTP 403 Forbidden** status means the server received and understood the request, but refuses to authorize it (access is denied). 

I follow a systematic top-to-bottom troubleshooting methodology:

---

### Step 1: Identify Which Layer is Generating the 403
Check whether the 403 is originating from the Cloud Edge (WAF/CloudFront), the Ingress controller, or the backend application itself:
- **Inspect Response Headers:** Using `curl -Iv https://app.domain.com`:
  - `Server: CloudFront` or header `x-amzn-waf-action: block` ➔ **AWS WAF / CDN issue**.
  - `Server: openresty` or `nginx` with standard HTML error page ➔ **Ingress / Reverse Proxy issue**.
  - Custom JSON body (e.g., `{"error": "Forbidden", "code": 403}`) ➔ **Application / Authorization issue**.

---

### Step 2: Check Web Application Firewall (AWS WAF) & CloudFront
- If using AWS WAF on ALB or CloudFront, check CloudWatch WAF metrics and sampled logs:
  - Verify if a newly deployed WAF rule (such as rate limiting, geo-blocking, or SQLi false-positive) is blocking client IPs.
  - If blocked, adjust the rule action from `Block` to `Count` temporarily to verify.

---

### Step 3: Check Ingress Controller & Reverse Proxy Configuration
- Inspect Ingress controller access logs:
  ```bash
  kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=100
  ```
- Common causes at the Ingress layer:
  - **IP Whitelist Annotation:** A misconfigured `nginx.ingress.kubernetes.io/whitelist-source-range` blocking incoming traffic.
  - **Missing SSL Client Certificate:** If mutual TLS (mTLS) was enabled accidentally.

---

### Step 4: Check Web Server & File System Permissions
- If the application runs NGINX/Apache serving static assets or frontend files:
  - Verify file permissions inside the container: web server users (`nginx` or `www-data`) must have read permissions (`chmod 644` for files, `chmod 755` for directories).
  - Verify `index.html` exists in the document root; without it and with auto-indexing disabled, NGINX returns 403 Forbidden.

---

### Step 5: Check Application Authentication & RBAC (JWT / IAM)
- Inspect application container logs:
  ```bash
  kubectl logs <pod-name> -n <namespace> --tail=100
  ```
- Check authorization failures:
  - Expired or invalid JWT token passed by the client.
  - Role-based authorization rules (e.g., user account lacks `admin` role required for the requested endpoint).
  - Cross-Origin Resource Sharing (CORS) origin rejection.
</details>

<summary><strong>● Suppose you receive a large number of production alerts simultaneously. How would you go about reducing alert noise and preventing alert fatigue?</strong></summary>

**Answer:**
Alert fatigue is a serious operational challenge where teams become desensitized to notifications due to high noise. 

I apply the following multi-step strategy to eliminate noise and maintain high alert hygiene:

---

### 1. Alert Deduplication & Aggregation (Alertmanager / PagerDuty)
- Configure **`group_by`** in Prometheus Alertmanager and PagerDuty:
  - Group alerts by `cluster`, `namespace`, and `alertname` over a window (e.g., `group_wait: 30s`, `group_interval: 5m`).
  - If 50 pods in a microservice crash simultaneously, the team receives **1 grouped notification** instead of 50 individual pages.

---

### 2. Strict Severity Categorization
Separate actionable critical issues from non-urgent warnings:
| Severity | Description | Notification Channel | Action Required |
| :--- | :--- | :--- | :--- |
| **P1 - Critical** | Direct customer impact (outage, data loss, API error rate > 5%) | PagerDuty (Phone call / Loud push notification) | Immediate 24/7 on-call response |
| **P2 - Warning** | Resource pressure (CPU > 80%, disk > 75%, single pod restart) | Dedicated Slack channel (`#alerts-warning`) | Triage during business hours |
| **P3 - Informational**| Routine maintenance, backup finished, deployment successful | Daily summary dashboard | No immediate action |

---

### 3. Replace Static Thresholds with Duration Windows
- Avoid alerting on instantaneous spikes (e.g., CPU reaching 90% for 5 seconds during container startup).
- Add evaluation periods:
  ```yaml
  - alert: HighCPUUsage
    expr: sum(rate(container_cpu_usage_seconds_total[5m])) by (pod) > 0.85
    for: 10m  # Must stay above 85% continuously for 10 minutes before firing!
  ```

---

### 4. Alert on User-Facing Symptoms (SRE Principle)
- Focus alerts on **symptoms** (e.g., high HTTP latency, 5xx error rates, failed payments) rather than internal root causes (e.g., high memory).
- If a server has 90% memory utilization but latency and error rates are healthy, it should not page an engineer at night.

---

### 5. Configure Alert Inhibition Rules
- Suppress secondary derivative alerts when the primary component fails:
  - If a worker node goes down (`NodeNotReady`), Alertmanager **inhibits** all downstream alerts (e.g., `PodCrashLooping`, `ContainerKilled`) originating from that specific node.

---

### 6. Conduct Regular Alert Hygiene Reviews
- Review alert history bi-weekly:
  - Identify the "top 5 noisiest alerts."
  - If an alert fires frequently without requiring manual action, either tune its threshold or delete it.

<summary><strong>● What is the difference between an AWS IAM Role and an IAM Policy?</strong></summary>

**Answer:**
In AWS Identity and Access Management (IAM), **Roles** and **Policies** work together to secure resources, but serve distinct purposes:

---

### Core Concept:
- **IAM Policy:** A JSON document that defines **permissions** (what actions are allowed or denied, and on which AWS resources). A policy does not represent an identity and cannot authenticate on its own.
- **IAM Role:** An AWS **identity** with permission policies attached to it. Unlike IAM Users, a role does not have permanent credentials (no password or access keys); instead, it provides temporary security credentials when assumed by a trusted entity.

---

### Comparison Matrix:

| Feature | IAM Policy | IAM Role |
| :--- | :--- | :--- |
| **What It Is** | Permissions document (Rules) | An Identity (Actor) |
| **Credentials** | None | Temporary session credentials via AWS STS (`AssumeRole`) |
| **Contents** | JSON statements (`Effect`, `Action`, `Resource`, `Condition`) | Trust Policy (who can assume it) + Permissions Policies |
| **Attachment** | Attached to Users, Groups, or Roles | Assumed by EC2, Lambda, EKS pods, or external AWS accounts |
| **Analogy** | A security badge access checklist | The badge holder (role) wearing the badge |

---

### Real-World Example:
1. You write an **IAM Policy** allowing read access to an S3 bucket:
   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Action": ["s3:GetObject"],
       "Resource": "arn:aws:s3:::company-app-data/*"
     }]
   }
   ```
2. You create an **IAM Role** with a Trust Policy allowing the **EC2 service** (`ec2.amazonaws.com`) to assume it.
3. You attach the policy to the role and associate the role with an EC2 instance via an **Instance Profile**. The EC2 instance accesses S3 securely without any hardcoded credentials.
</details>

<details>
<summary><strong>● What is a Dead Letter Queue (DLQ) in Amazon SQS?</strong></summary>

**Answer:**
A **Dead Letter Queue (DLQ)** in Amazon SQS is a secondary queue used to catch and isolate messages that could not be successfully processed by a consumer application after a maximum number of attempts.

---

### 1. How a DLQ Works:
1. A producer publishes messages to a primary SQS queue.
2. A consumer attempts to process a message but fails (due to invalid payload schema, unhandled application crash, or database timeout).
3. The message becomes invisible for the duration of the `VisibilityTimeout`. Once that timer expires, the message reappears in the queue for another consumer to retry.
4. Each time a message is received, SQS increments its `ReceiveCount`.
5. When `ReceiveCount` exceeds the configured **Maximum Receives (`maxReceiveCount`)** (e.g., 3 or 5), SQS automatically removes the problematic message from the primary queue and moves it into the **DLQ**.

---

### 2. Why Use a DLQ (Key Operational Benefits):
- **Prevents "Poison Pill" Loops:** Prevents corrupt or malformed messages from blocking the primary queue or continuously crashing worker pods in an infinite loop.
- **Isolates Failures for Debugging:** Keeps failed messages safe for engineers to inspect payloads, identify bugs, and analyze errors.
- **Alerting & Monitoring:** CloudWatch Alarms can be attached to the DLQ (`ApproximateNumberOfMessagesVisible > 0`) to immediately notify the team of unhandled processing failures.
- **DLQ Redrive Capability:** Once the application bug is resolved, AWS SQS provides a built-in **Redrive** feature that moves the messages back from the DLQ into the source queue to be reprocessed safely.
</details>

<summary><strong>↳ Follow-up: Suppose an application sends messages to an Amazon SQS queue, and an AWS Lambda function is configured as the consumer, but the Lambda function is not consuming the messages from the queue. How would you troubleshoot this issue?</strong></summary>

**Answer:**
When an AWS Lambda function fails to consume messages from an SQS queue, the issue typically lies in the event source mapping, IAM permissions, concurrency limits, or network routing:

---

### Step 1: Verify the SQS Event Source Mapping (ESM)
- Check whether the event mapping between SQS and Lambda is **Enabled** and **Active**:
  ```bash
  aws lambda list-event-source-mappings --function-name <function-name>
  ```
- If the mapping state is `Disabled`, `Enabling`, or `Error`, Lambda will not poll SQS. Check the `LastProcessingResult` field for error messages.

---

### Step 2: Check Lambda Execution IAM Role Permissions
- Lambda needs specific IAM permissions to poll and manage SQS messages. Verify the Lambda execution role contains:
  - `sqs:ReceiveMessage`
  - `sqs:DeleteMessage`
  - `sqs:GetQueueAttributes`
- **Recommended Managed Policy:** Attach `AWSLambdaSQSQueueExecutionRole`.

---

### Step 3: Check SQS KMS Encryption Permissions
- If the SQS queue is encrypted using a **Customer Managed Key (CMK)** via AWS KMS:
  - The Lambda execution role must have `kms:Decrypt` permission on the KMS key policy.
  - Without KMS decrypt permissions, Lambda will fail to read messages silently or disable the event mapping.

---

### Step 4: Check Lambda Concurrency & Throttling
- Check CloudWatch metrics for the Lambda function:
  - **Throttles:** If account-wide or function-specific reserved concurrency is reached, invocations are throttled.
  - **Reserved Concurrency = 0:** If reserved concurrency is set to `0`, the function is completely disabled from running.

---

### Step 5: Check Lambda CloudWatch Execution Logs & Errors
- Review `/aws/lambda/<function-name>` log groups in CloudWatch:
  - Check for application syntax errors, missing environment variables, or runtime crashes.
  - Check for Lambda timeout errors (`Task timed out after X seconds`): if the timeout is set too low (e.g., 3s), the invocation will terminate before completing.

---

### Step 6: Check VPC & Security Group Configuration (If Lambda is in a VPC)
- If the Lambda function is deployed inside an Amazon VPC:
  - It cannot reach SQS unless the subnet has a route to a **NAT Gateway** or an **Interface VPC Endpoint for SQS (`com.amazonaws.<region>.sqs`)**.
  - Ensure the security group attached to the Lambda ENI allows outbound HTTPS (port 443) traffic.

<summary><strong>● When you run 'terraform init' for the first time, what happens internally, especially with regard to the backend?</strong></summary>

**Answer:**
When executing `terraform init` for the first time in a new configuration directory, Terraform performs three major internal initialization steps:

---

### 1. Backend Initialization (State Storage Setup)
- **Inspects Backend Configuration:** Reads the `backend "s3"` block in your code.
- **Validates Remote Infrastructure:** Connects to AWS to verify the specified S3 bucket exists and is accessible.
- **Initializes State Pointer:** Prepares the remote state file (`terraform.tfstate`). If it doesn't exist yet, Terraform registers the path where it will be written upon first apply.
- **Configures State Locking:** Validates the DynamoDB table specified for state locking (`dynamodb_table`).
- **Writes Local Metadata:** Creates a local hidden directory `.terraform/` and writes `.terraform/terraform.tfstate`, which stores the backend configuration and state schema pointers so subsequent commands (`plan`, `apply`) communicate directly with S3.

---

### 2. Provider Plugin Installation
- **Reads Requirements:** Examines the `required_providers` block (e.g., `hashicorp/aws`, `hashicorp/kubernetes`).
- **Downloads Binaries:** Queries the Terraform Registry, downloads the provider plugin binaries compatible with your OS/CPU architecture, and unpacks them into `.terraform/providers/`.
- **Generates Dependency Lock File (`.terraform.lock.hcl`):** Creates or updates the lock file with cryptographic SHA256 hashes of the provider binaries. This ensures every team member and CI/CD runner uses identical provider versions.

---

### 3. Child Module Installation
- If the configuration references child modules (`module "vpc" { source = "..." }`):
  - Copies local modules or clones Git/Registry modules into `.terraform/modules/`.
</details>

<details>
<summary><strong>● Are you familiar with Terraform meta-arguments, and what is the difference between 'count' and 'for_each'?</strong></summary>

**Answer:**
Yes, **meta-arguments** in Terraform are special configuration arguments (such as `count`, `for_each`, `depends_on`, `lifecycle`, and `provider`) that modify the lifecycle or behavior of resources and modules.

The primary difference between `count` and `for_each` is how they manage multiple resource instances:

---

### Comparison Matrix:

| Feature | `count` | `for_each` |
| :--- | :--- | :--- |
| **Input Data Type** | An integer (`count = 3`) | A `map` or `set of strings` (`toset(["a", "b"])`) |
| **Resource Addressing** | Indexed list: `aws_subnet.app[0]`, `[1]`, `[2]` | Key-based: `aws_subnet.app["us-east-1a"]`, `["us-east-1b"]` |
| **Middle Element Removal** | **Risk of destruction:** Removing an item in the middle changes all subsequent indices, causing Terraform to **destroy and recreate** unintended resources! | **Safe:** Removing a key deletes only that specific instance; all other resources remain untouched. |
| **Resource Uniqueness** | Best for identical resources or conditional toggles. | Best for heterogeneous resources with unique names, CIDRs, or configurations. |

---

### Practical Examples:

#### 1. When to Use `count` (Conditional Creation Toggle):
```hcl
variable "enable_bastion" {
  type    = bool
  default = false
}

resource "aws_instance" "bastion" {
  count         = var.enable_bastion ? 1 : 0
  ami           = "ami-12345678"
  instance_type = "t3.micro"
}
```

#### 2. When to Use `for_each` (Distinct Subnets by AZ):
```hcl
variable "subnets" {
  type = map(string)
  default = {
    "us-east-1a" = "10.0.1.0/24"
    "us-east-1b" = "10.0.2.0/24"
  }
}

resource "aws_subnet" "app" {
  for_each          = var.subnets
  vpc_id            = aws_vpc.main.id
  cidr_block        = each.value
  availability_zone = each.key
  tags = { Name = "subnet-${each.key}" }
}
```
</details>

<summary><strong>● Suppose you have two Terraform modules, a VPC module and an EKS module, and you created subnets in the VPC module that you want to use in the EKS module. How would you pass the subnet IDs between these two modules?</strong></summary>

**Answer:**
In Terraform, modules are self-contained. Resources inside one module are private and cannot be directly queried by another module. 

To pass subnet IDs from a VPC module to an EKS module, we use **Module Outputs** and **Module Input Variables**:

---

### Step 1: Define an Output in the VPC Module (`modules/vpc/outputs.tf`)
Export the subnet IDs as an output:
```hcl
output "private_subnet_ids" {
  description = "List of private subnet IDs for EKS worker nodes"
  value       = aws_subnet.private[*].id
}
```

---

### Step 2: Define an Input Variable in the EKS Module (`modules/eks/variables.tf`)
Declare an input variable to receive the IDs:
```hcl
variable "subnet_ids" {
  description = "Subnet IDs where EKS cluster and node groups will be provisioned"
  type        = list(string)
}
```

---

### Step 3: Wire Them Together in the Root Module (`main.tf`)
Reference the output of the VPC module as the argument for the EKS module:
```hcl
module "vpc" {
  source   = "./modules/vpc"
  vpc_cidr = "10.0.0.0/16"
}

module "eks" {
  source       = "./modules/eks"
  cluster_name = "devon-prod-eks"
  # Pass the output from VPC module here:
  subnet_ids   = module.vpc.private_subnet_ids
}
```

---

### Alternative Method (When State Files Are Separated):
If VPC and EKS are in completely separate repositories with distinct state files, use the **`terraform_remote_state`** data source in the EKS root module:
```hcl
data "terraform_remote_state" "vpc" {
  backend = "s3"
  config = {
    bucket = "company-tf-states"
    key    = "vpc/terraform.tfstate"
    region = "us-east-1"
  }
}

module "eks" {
  source     = "./modules/eks"
  subnet_ids = data.terraform_remote_state.vpc.outputs.private_subnet_ids
}
```
</details>

<summary><strong>● Suppose you have three environments—Development, Staging, and Production—and you need to provision VPC, EC2, and EKS infrastructure in all three without duplicating Terraform code. How would you design and manage this setup?</strong></summary>

**Answer:**
To manage multi-environment infrastructure cleanly without code duplication, the industry-standard architecture is **Directory-Based Environment Separation using Reusable Child Modules**:

---

### 1. Recommended Directory Structure:
```text
terraform-infrastructure/
├── modules/                      # Reusable, shared module code (DRY)
│   ├── vpc/
│   │   ├── main.tf
│   │   ├── variables.tf
│   │   └── outputs.tf
│   ├── eks/
│   └── ec2/
└── environments/                 # Environment-specific caller configurations
    ├── dev/
    │   ├── main.tf               # Calls modules with dev variables
    │   ├── backend.tf            # Backend: s3 key = "dev/terraform.tfstate"
    │   └── terraform.tfvars      # dev-specific sizing (e.g. 2 nodes, t3.medium)
    ├── staging/
    │   ├── main.tf
    │   ├── backend.tf            # Backend: s3 key = "staging/terraform.tfstate"
    │   └── terraform.tfvars      # staging-specific sizing
    └── prod/
        ├── main.tf
        ├── backend.tf            # Backend: s3 key = "prod/terraform.tfstate"
        └── terraform.tfvars      # prod-specific sizing (e.g. 6 nodes, m5.large)
```

---

### 2. Key Benefits of This Architecture:
1. **Zero Code Duplication:** The underlying logic for creating VPCs, EKS clusters, and Security Groups lives only once in `modules/`.
2. **Blast Radius Isolation:** Each environment maintains its own isolated S3 backend state file. A failure or corruption in `dev` has zero possibility of damaging `prod`.
3. **Environment Sizing Flexibility:** Low-cost parameters are passed to `dev.tfvars` while high-availability parameters (multi-AZ, larger instance types) are passed to `prod.tfvars`.
4. **Independent Promotion & RBAC:** CI/CD pipelines can apply changes to `dev` automatically upon PR merge, while `prod` requires manual approvals.
</details>

<details>
<summary><strong>↳ Follow-up: Apart from using modules, is there any other way to avoid duplicating Terraform code across environments?</strong></summary>

**Answer:**
Yes, several alternative tools and patterns exist to keep Terraform configurations DRY:

---

### 1. Terragrunt (Enterprise DRY Orchestrator)
- **Terragrunt** is an open-source wrapper for Terraform specifically built to eliminate code duplication:
  - Centralizes backend configurations and provider declarations in a single root `terragrunt.hcl`.
  - Environment directories only contain a small `terragrunt.hcl` file referencing the module source and supplying environment-specific `inputs = { ... }`.

---

### 2. Terraform Workspaces
- Allows managing multiple state instances (e.g., `dev`, `staging`, `prod`) from a single set of `.tf` files:
  - Command: `terraform workspace select dev` or `terraform workspace new prod`.
  - Interpolate environment in code: `instance_type = terraform.workspace == "prod" ? "m5.large" : "t3.small"`.
  - *Trade-off:* All workspaces share the same code version; risk of human error if an engineer applies changes in the wrong workspace.

---

### 3. Dynamic Variable Files via CI/CD (`-var-file`)
- Maintain a single root configuration directory and manage environment variations strictly through separate `.tfvars` files:
  - `terraform apply -var-file=config/dev.tfvars`
  - `terraform apply -var-file=config/prod.tfvars`
  - CI/CD pipelines (Jenkins / GitHub Actions) inject the appropriate variable file and backend key dynamically during execution.

---

### 4. Terraform Cloud / Spacelift Workspaces
- Use managed cloud platforms where a single VCS repository branch connects to multiple cloud workspaces, and environment variables are injected securely through the platform UI.
</details>

<summary><strong>● What is the difference between an SLA (Service Level Agreement) and an SLO (Service Level Objective)?</strong></summary>

**Answer:**
In Site Reliability Engineering (SRE), **SLA**, **SLO**, and **SLI** form the core framework for measuring system reliability:

---

### Comparison Matrix:

| Concept | What It Stands For | Definition & Scope | Audience | Penalty / Consequence |
| :--- | :--- | :--- | :--- | :--- |
| **SLA** | **Service Level Agreement** | A formal, legally binding commitment between service provider and customer. | External customers, business leaders, legal teams | Financial penalties, customer credits, or contract breach |
| **SLO** | **Service Level Objective** | An internal target goal set by the engineering and SRE team for system reliability. | Internal developers, SREs, product managers | Triggers deployment freezes and Error Budget replenishment (No legal penalties) |
| **SLI** | **Service Level Indicator** | The actual real-time metric measured over time (e.g., latency, error rate). | Monitoring tools, dashboards, on-call engineers | Feeds into SLO tracking |

---

### Practical SRE Example:
- **SLI (What we measure):** The percentage of successful HTTP API requests:
  $$\text{SLI} = \frac{\text{Successful Requests (2xx, 3xx)}}{\text{Total Requests}} \times 100$$
- **SLA (External Commitment):** "The platform guarantees 99.9% availability per month. If availability falls below 99.9%, customers receive a 10% billing credit."
- **SLO (Internal Goal):** The internal engineering team sets the SLO at **99.95%** (stricter than the 99.9% SLA).
- **The Error Budget Safety Buffer:** The 0.05% difference represents the safety buffer. If internal error budgets are burning too fast, the team halts new feature deployments to focus on reliability before ever breaching the customer SLA!
</details>

<summary><strong>● Have you created or maintained any operational runbooks?</strong></summary>

**Answer:**
Yes, creating and maintaining operational runbooks is a vital part of my DevOps and SRE responsibilities to reduce **Mean Time to Recovery (MTTR)** and standardize incident handling across on-call engineers.

---

### Standard Structure of Runbooks I Created:
1. **Overview & Trigger:** The exact alert name and condition (e.g., `Alert: HighMemoryUtilization > 90% on OrderService`).
2. **Severity & Escalation:** Severity level (P1/P2), target resolution SLA, and secondary on-call contact details.
3. **Immediate Mitigation Steps:** Safe actions to restore customer availability immediately (e.g., scale pods, restart stuck deployment, route traffic away).
4. **Diagnostic Commands:** Ready-to-use CLI commands to inspect the live state:
   - `kubectl top pods -n prod`
   - `kubectl describe pod <pod-name> -n prod`
   - `kubectl logs <pod-name> -n prod --previous`
5. **Root Cause Analysis (RCA) Guide:** Log queries for Kibana / CloudWatch Logs Insights and known past fixes.
6. **Verification & Post-Resolution:** Steps to confirm system health and metrics return to normal baseline before closing the incident ticket.

---

### Examples of Production Runbooks I Maintained:
- **Runbook 1: Kubernetes Pod `CrashLoopBackOff` & `OOMKilled` Remediation:** Detailed steps to inspect exit code 137, adjust memory requests/limits in Helm `values.yaml`, and trigger safe rollouts.
- **Runbook 2: Ingress 502/503 Bad Gateway Resolution:** Steps to verify Service endpoint discovery, check CoreDNS pods, and validate container readiness probe response codes.
- **Runbook 3: Amazon RDS High CPU & Connection Pool Exhaustion:** Steps to identify slow queries via Performance Insights, restart misbehaving client connection pools, or scale read replicas.
- **Runbook 4: Automated SSL/TLS Certificate Emergency Renewal:** Step-by-step procedure to rotate expiring ACM/Let's Encrypt certificates without downtime.
