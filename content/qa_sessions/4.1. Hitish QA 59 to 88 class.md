Instructor's Elaboration on the DevSecOps Flow: Adding security to pipelines is a major industry trend. The flow he described should look like this:

SCA (Software Composition Analysis): Right after code checkout, you run a file system scan to check for exposed secrets or vulnerabilities in your dependencies. Tools like Trivy or plugins like Jacoco can be used here. If vulnerabilities are found, the pipeline should fail.

**Technical Answer & Guidance**

* **Architectural Differences:**  
  * **Cluster Autoscaler (CAS):** Strongly coupled to cloud-provider node abstractions (e.g., AWS Auto Scaling Groups / Node Groups). When pods are unschedulable, CAS triggers the ASG to scale up, resulting in slower provisioning times (minutes) and limited flexibility in mixed-instance sizing.

It evaluates pending pod specifications (CPU, memory, tolerations, topology spreads) and provisions optimally sized nodes within seconds.  
  * **Node Consolidation & Cost Optimization:** Karpenter actively reorganizes workloads and de-provisions or downscales underutilized nodes automatically to save cloud spend.  
* **Interview Strategy & Project Framing:**  
  * You do not need to claim full multi-year production ownership. Frame it as an evaluated initiative:  
    *"In our production cluster, we initially ran Cluster Autoscaler. However, due to node provisioning latency and overhead with static node groups, I conducted a Proof of Concept (POC) evaluating Karpenter. I benchmarked cold-start provisioning speeds, automated bin-packing, and cost reduction, demonstrated the demo to the engineering team, and we initiated a roadmap to adopt it."*

**12\. Terraform Count vs. For\_Each**

* **Primary Question:** In Terraform, what is the difference between count and for\_each, and when would you choose one over the other? Can you provide an example?  
* **Recommended Solution:**  
  * count: Iterates over an integer or list, indexing resources by numerical index (\[0\], \[1\]). Removing an element from the middle of the list causes Terraform to re-create subsequent resources due to index shifting.  
  * for\_each: Iterates over a map or set of strings, binding resources to distinct keys (\["resource\_name"\]). Modifying or removing an item only impacts that specific key without re-creating other resources.  
  * **When to choose:** Use count for identical duplicates or simple feature toggles (count \= var.enabled ? 1 : 0). Use for\_each for collections of named, distinct resources.

**Question 2: ConfigMap Update Propagation & Troubleshooting**

* **Primary Question:** You updated a Kubernetes ConfigMap, but the application pods continue to use the old values. Why does this occur, and how do you troubleshoot and resolve it?  
* **Core Technical Answer:**  
  * **Root Causes:**  
    1. *Environment Variables (env / envFrom):* Kubernetes evaluates environment variables only during container startup. Changes to the underlying ConfigMap **never** propagate automatically to environment variables in running pods.  
    2. *Volume Mounts with SubPath (subPath):* ConfigMaps mounted using subPath do not receive automated updates.  
    3. *Kubelet Sync Period & Cache:* If mounted as a standard volume directory, updates propagate automatically via symlinks, but there is an inherent delay governed by the Kubelet sync loop and TTL cache (typically up to 1–2 minutes).  
    4. *Application In-Memory Caching:* The application runtime may read the file once at startup and cache the configuration in memory.  
  * **Remediation:** Trigger a rolling restart of the deployment (kubectl rollout restart deployment/\<name\>) to pick up new environment variables or force application reload. Alternatively, integrate tools like Reloader (stakater) to automatically restart pods on ConfigMap hash changes.

**Question 3: Container Health Checks (Liveness, Readiness, Startup)**

* **Primary Question:** What are the key differences between Liveness, Readiness, and Startup probes in Kubernetes?  
* **Core Technical Answer:**  
  * **Startup Probe:** Validates whether the application has finished its initial boot process (e.g., loading large caches, database schemas, or models). All other probes are disabled until the startup probe passes. If it fails beyond failureThreshold, the kubelet kills and restarts the container.  
  * **Readiness Probe:** Determines whether the container is ready to accept user network traffic. If it fails, Kubernetes removes the pod's IP from the matching Service’s Endpoints/EndpointSlices so no traffic is routed to it. It does **not** restart the container.  
  * **Liveness Probe:** Detects deadlocks, internal crashes, or unrecoverable hanging states where the process is running but unresponsive. If it fails beyond the threshold, the kubelet kills the container and initiates a restart according to its restartPolicy.

**Question 7: Ingress Controllers vs. Standard Kubernetes Services**

* **Primary Question:** Why do we need an Ingress resource and Ingress Controller when Kubernetes Services (ClusterIP, NodePort, LoadBalancer) already exist?  
* **Core Technical Answer:**

  * **Layer 7 Routing:** Ingress operates at Layer 7 (HTTP/HTTPS), allowing multiple services to sit behind a single shared Load Balancer with intelligent host-based routing (e.g., api.domain.com vs. app.domain.com) and path-based routing (e.g., /users vs. /orders).

**Question 8: AWS Transit Gateway vs. VPC Peering**

* **Primary Question:** Why do we need an AWS Transit Gateway when VPC Peering is already available?  
* **Core Technical Answer:**  
  * **Non-Transitive Peering Limitation:** VPC Peering is strictly point-to-point and **non-transitive** (if VPC A is peered to B, and B to C, A cannot talk to C). Connecting $N$ VPCs requires an $N(N-1)/2$ mesh of peering connections, which becomes unmanageable at scale.  
  * **Hub-and-Spoke Centralization:** Transit Gateway acts as a central cloud router (hub-and-spoke). Hundreds of VPCs, AWS Direct Connect connections, and on-premises VPN connections attach to a single gateway with centralized route tables, traffic inspection (firewalls), and simplified governance.

**Question 9: AWS VPC Subnet Classification (Public vs. Private)**

**Question 13: Distroless Container Images**

**Question 19: Reducing EKS Costs with Low CPU Utilization**

* **Primary Question:** Your AWS EKS cluster billing has increased significantly even though average CPU utilization remains low. How do you reduce costs without compromising system reliability?  
* **Instructor Guidance & Technical Solution:**  
  * The instructor noted that simply adding nodes via an autoscaler can worsen costs when utilization is low, and highlighted these core remedies:  
    1. **Workload Right-Sizing (Requests & Limits):** The Kubernetes scheduler schedules pods based on resource **requests**, not real-time usage. If developers request 4 vCPUs for a pod that only utilizes 0.2 vCPUs, nodes will appear 100% committed to the scheduler, triggering unnecessary node scale-outs while actual CPU utilization sits at 5%. Use the **Vertical Pod Autoscaler (VPA)** in recommendation mode or tools like Kubecost/Goldilocks to tune requests to match real P95 usage.  
    2. **Modern Node Autoscaling with Karpenter:** Replace the legacy Cluster Autoscaler with **Karpenter**. Karpenter evaluates pending pods, bypasses rigid EC2 Auto Scaling Groups, provisions optimally sized instances just-in-time, and automatically bin-packs and consolidates workloads onto cheaper node types while terminating underutilized instances.  
    3. **Leverage Spot Instances:** Migrate stateless, fault-tolerant workloads to EC2 Spot Instances (saving up to 70–90%) coupled with proper Pod Disruption Budgets (PDB) and graceful node termination handlers.  
    4. **Purchasing Options:** For steady-state baseline compute, purchase **AWS Compute Savings Plans** or Reserved Instances.  
    5. **Pruning Idle Resources:** Audit and eliminate dangling unused EBS volumes, unattached Elastic IPs, and unused Application Load Balancers.

**Question 20: Multi-Tenant Cluster Isolation & Limitations**

* **Primary Question:** Multiple teams share a single EKS cluster. How do you prevent teams from accessing each other's workloads, secrets, and resources?  
* **Sub-Question:** What are the fundamental limitations of relying solely on Kubernetes namespace isolation?  
* **Core Technical Answer:**  
  * **Enforcing Multi-Tenancy:**  
    * *Namespaces & RBAC:* Create dedicated namespaces per team/tenant with strict Kubernetes Role-Based Access Control (Role, RoleBinding) mapping to IAM identities.  
    * *Resource Quotas & LimitRanges:* Apply ResourceQuota to cap CPU, memory, and storage per namespace, preventing one tenant from starving the cluster (noisy neighbor problem). Apply LimitRange for default pod requests/limits.  
    * *NetworkPolicies:* Isolate inter-namespace network traffic by default.  
  * **Limitations of Namespace Isolation (Soft Multi-Tenancy):**  
    * Namespaces are **logical boundaries, not physical or security boundaries**.  
    * *Shared Kernel:* All containers on a node share the host Linux kernel. A container breakout or kernel vulnerability compromises the entire node across all tenants.  
    * *Cluster-Scoped Resources:* CRDs, StorageClasses, IngressControllers, and Nodes are cluster-scoped and shared.  
    * *Kubelet & Network Saturation:* A rogue container can saturate node I/O, network bandwidth, or fill local ephemeral storage (/var/lib/docker or /var/lib/kubelet), impacting neighboring pods regardless of namespaces.  
    * *Strict Isolation Requirement:* For hard multi-tenancy (untrusted tenants or strict compliance), teams must use dedicated node groups with node taints/tolerations (nodeAffinity), microVM runtime isolators (e.g., AWS Firecracker / Kata Containers), or separate clusters.
