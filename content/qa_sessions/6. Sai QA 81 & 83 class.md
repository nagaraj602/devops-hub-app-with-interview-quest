**2\. Git & Version Control Scenarios**  
**Questions Asked**

* **Primary Question:** "Between whom or under what conditions does a merge conflict occur?"  
* **Scenario Question:**  
  *"Developer A creates branch-A from main, modifies lohit.sh, and merges branch-A into main. Subsequently, Developer B creates branch-B from main (which already has Developer A's changes), makes further modifications to lohit.sh, and attempts to merge branch-B into main. Will Developer B encounter a merge conflict?"*  
* **Sub-Question 1:** "In which scenario or concept will you actually see a merge conflict occur?"

**Technical Explanation & Solution**

* **Scenario Resolution:** In the sequential scenario presented, **no merge conflict occurs**. Because Developer B branched off main *after* Developer A's changes were already merged, Developer B’s branch already contains Developer A's commit history. When Developer B merges, Git performs a standard clean fast-forward or non-conflicting merge.  
* **When Conflicts Actually Occur:** A merge conflict occurs when two branches diverge from a common base commit, both developers modify the **exact same lines** of the **same file** independently, and one branch is merged into the target branch first. When the second branch attempts to merge, Git cannot determine which version of those specific lines takes precedence.

**3\. Branching Strategies & Pre-Merge Quality Gates**  
**Questions Asked**

* **Primary Question:** "What branching strategy do you use in your organization?"  
* **Sub-Question 1:** "Why is your organization still using master instead of main?"  
* **Sub-Question 2:** "What is a 'Pre-Merge Quality Gate'?"  
* **Sub-Question 3:** "What exact checks, processes, and tools are included in the Pre-Merge Quality Gate before code is allowed to merge into the dev branch?"

**Technical Explanation & Solution**

* **Branching Model:** A standard environment-driven model consists of feature branches (feature/\*), dev, staging (or uat), and main/production. Legacy repositories often retain master due to legacy CI/CD configurations, webhook hooks, or policy inertia.  
* **Pre-Merge Quality Gate Defined:** A Pre-Merge Quality Gate is an automated set of validation checks enforced at the Pull Request (PR) stage that must pass before code can be merged into protected integration branches (dev, staging, main).  
* **Components of a Pre-Merge Quality Gate:**  
  1. **Unit Testing:** Automated unit tests (e.g., JUnit for Java) executed locally or in a PR build runner.  
  2. **Static Code Analysis (SAST):** SonarQube analysis for bugs, security hotspots, code smells, and adherence to minimum code coverage thresholds.  
  3. **Vulnerability & IaC Scanning:** Trivy scanning of the repository, dependencies, and configuration files (e.g., Dockerfiles).  
  4. **Peer/Admin Approval:** Mandatory branch protection policies requiring code reviews and approvals (typically 1–2 senior engineers/admins).

**4\. Static Code Analysis & SonarQube Deep Dive**  
**Questions Asked**

* **Primary Question:** "What exactly are you doing with SonarQube in your pipeline?"  
* **Sub-Question 1:** "What does 'code duplication' mean in SonarQube? If functions are designed to be reused repeatedly, does every function call count as duplication?"  
* **Sub-Question 2:** "What is Static Code Analysis? Does it run before or after Maven builds the binary package (artifact)?"  
* **Sub-Question 3:** "What is code coverage, and how is it calculated and verified?"  
* **Sub-Question 4:** "If code coverage falls below the required threshold (e.g., 80%), what command or mechanism is used in the Jenkins pipeline to fail the build? What exit code is returned?"

**Technical Explanation & Solution**

* **Static Code Analysis Timing:** Static code analysis inspects source code without executing the application. It runs **before** the final binary artifact (JAR/WAR) is packaged or deployed, or as part of the compilation step (e.g., using Maven's mvn sonar:sonar). Scanning an already-packaged binary artifact is binary/composition analysis, not SAST.  
* **Code Duplication vs. Reuse:** Code duplication refers to identical or nearly identical blocks of logic copy-pasted across different files or methods, increasing maintenance overhead. Reusable functions adhere to the DRY (Don't Repeat Yourself) principle and are **not** flagged as duplicate code.  
* **Code Coverage:** Code coverage measures the percentage of source code lines, branches, and instructions executed during automated unit test execution. A coverage tool (e.g., JaCoCo for Java) generates an execution report that SonarQube ingests to enforce thresholds (e.g., \$\\ge 80\\%\$).  
* **Jenkins Quality Gate Enforcement:**  
  * Jenkins does not evaluate coverage calculations natively; it queries the SonarQube Quality Gate webhook/API using the SonarQube Scanner plugin.  
  * In scripted or declarative Jenkins pipelines, the step waitForQualityGate() pauses execution until SonarQube returns the status.  
  * If the quality gate status returns FAILED or ERROR, the step automatically throws an error and exits with **exit 1** (non-zero exit code), intentionally aborting the pipeline and blocking the PR from merging.

**5\. Security & Vulnerability Scanning with Trivy**  
**Questions Asked**

* **Primary Question:** "What scans are you executing with Trivy in your CI/CD pipeline?"  
* **Sub-Question 1:** "Why do you need to scan the Dockerfile?"  
* **Sub-Question 2:** "What is the difference between a 'misconfiguration' and a 'vulnerability'?"  
* **Sub-Question 3:** "If you scan the Dockerfile, and then build the image with docker build \-t and scan the image, aren't you scanning the same thing twice?"  
* **Sub-Question 4:** "Why does Trivy provide multiple distinct scan modes?"

**Technical Explanation & Solution**

Trivy operates at three distinct layers:

| Scan Type | Target | What It Detects | Why It Is Not Redundant |
| :---- | :---- | :---- | :---- |
| **Dockerfile Misconfiguration Scan** | Plaintext Dockerfile (IaC) | Dangerous instructions, running as root user, exposing insecure ports, missing health checks. | Catches architectural misconfigurations *before* the image is built. |
| **Container Image Scan** | Built container image (OCI/Docker layers) | Known CVEs in OS packages (Alpine/Ubuntu base layers) and application runtime libraries. | A Dockerfile can be syntactically perfect, but the base image (FROM ubuntu:20.04) or installed packages may contain hundreds of critical OS-level CVEs. |
| **Filesystem / Repo Scan** | Source code & package manifests | Vulnerable third-party dependencies (pom.xml, package-lock.json) and exposed secrets/tokens. | Audits dependencies and credentials without requiring containerization. |

*   
  **Misconfiguration vs. Vulnerability:**  
  * A **misconfiguration** is an insecure setting or practice (e.g., running containers with \--privileged, lack of resource limits, running as root).  
  * A **vulnerability** is a known, cataloged flaw or bug in software code or libraries that can be exploited by an attacker (tracked via CVE IDs).

**6\. Deployment, QA Automation, and Pipeline Integration**  
**Questions Asked**

* **Primary Question:** "Once changes are merged into the dev branch and deployed to the Dev environment, how does QA testing proceed?"  
* **Sub-Question 1:** "Is QA testing done manually or automated? Why can't an enterprise rely solely on manual testing?"  
* **Sub-Question 2:** "As a DevOps engineer, how do you help QA engineers reduce testing time from 2–4 hours down to automated pipeline execution?"  
* **Sub-Question 3:** "How does the QA automation framework integrate into the CI/CD pipeline?"  
* **Sub-Question 4:** "What is the distinction between Sanity testing and Integration/End-to-End (E2E) testing, and where are they executed?"

**Technical Explanation & Solution**

* **Risks of Pure Manual Testing:** Manual verification takes hours, introduces human error, fails to cover obscure edge cases consistently, and does not scale across frequent deployments. If a key tester leaves, undocumented manual test scenarios are lost.  
* **DevOps & QA Integration Workflow:**  
  * QA engineers write automated test scripts (e.g., using PyTest, Selenium, Cypress, or REST Assured).  
  * The DevOps engineer sets up post-deployment pipeline hooks.  
  * Once the deployment stage successfully releases the artifact to the dev or staging environment, Jenkins automatically triggers an automated testing job.  
  * The test pipeline spins up a headless test runner, executes the test suite against the live environment endpoints, and publishes the test report back to Jenkins/Slack.  
* **Test Classifications:**  
  * **Sanity/Smoke Tests:** A quick, lightweight set of tests executed immediately post-deployment to verify that the application has started correctly, core endpoints respond with 200 OK, and critical dependencies are accessible.  
  * **Integration / E2E Tests:** Comprehensive test suites validating multi-service communication, database transactions, third-party API flows, and user journeys across microservices in isolated or staging environments.

**7\. Core Architecture & Strategic Interview Questions**  
**Questions Asked**

* **Primary Question:** "Why do you use Docker and Kubernetes? Why can't you just deploy the application directly onto an AWS EC2 instance?"  
* **Sub-Question 1:** "How do you differentiate Continuous Integration (CI) and Continuous Delivery/Deployment (CD) in your organization?"  
* **Sub-Question 2:** "Why is it dangerous to answer interview questions with 'because my company uses this tool'?"

**Technical Explanation & Solution**

* **EC2 vs. Docker & Kubernetes:**  
  * Direct EC2 deployments require managing full virtual machines, resulting in slower provisioning times (minutes vs. seconds), lower compute density, manual OS patching, and complex multi-service isolation.  
  * Docker packages the application with all its dependencies, ensuring immutability across environments.  
  * Kubernetes provides automated bin-packing, self-healing (restarting failed containers), rolling zero-downtime updates, service discovery, ingress routing, and dynamic horizontal pod autoscaling (HPA) to handle traffic spikes.  
* **CI vs. CD:**  
  * **Continuous Integration (CI):** Automating code integration, compilation, unit testing, SAST, and packaging on every commit or PR.  
  * **Continuous Delivery (CD):** Automatically building, testing, and preparing code releases, with deployment to Staging/UAT automated and Production deployment gated by a manual approval.  
  * **Continuous Deployment (CD):** Every valid change that passes automated tests and quality gates is automatically deployed to Production without manual intervention.  
* **Answering the "Why":** Senior-level interviews focus heavily on trade-offs. Stating "we use tool X because the company uses it" reveals a lack of architectural understanding. Responses must always be anchored in technical and operational justifications: scalability, fault tolerance, resource optimization, security compliance, and developer velocity.

  * In a multibranch pipeline setup, how are branch events filtered so that each branch deploys only to its corresponding environment?

* **Suggested Answer / Guidance:**  
  * **Triggering Mechanism:** GitHub webhooks emit push/merge payload events. The multibranch pipeline evaluates the target branch matching rule and initiates the corresponding environment deployment stage.  
  * **Post-Deployment Validation:** CI finishes after code compilation, unit tests, code quality scans, container builds, and registry push (ECR). CD must not stop at deployment (`kubectl apply`); it must verify operational health.

  * **Testing Analogy Across Environments:**  
    * *Flight Journey (Dev Sanity):* Tests the "happy path" (basic health checks, essential service connectivity, 30–40 core test cases) to confirm immediate functionality without running heavy regression suites.  
    * *Train / Car Journey (Staging & Production Regression):* Comprehensive, end-to-end regression testing covering hundreds of edge cases across all integrated microservices to guarantee stability before production sign-off.  
    * *Automated Rollback:* If smoke or health checks fail, the pipeline triggers an automated rollback to the previous stable release.

  * **Sequential Minor Upgrades:** In Kubernetes/EKS, **minor versions cannot be skipped**. You must upgrade sequentially (e.g., `1.34` → `1.35` → `1.36`). Patch versions within the same minor version (e.g., `1.35.1` to `1.35.4`) can be upgraded directly.  
  * **Upgrade Cadence & Testing:**  
    * Patch releases for vulnerabilities and bug fixes are applied frequently (e.g., monthly).  
    * Major/minor version upgrades occur every 6 to 12 months.  
    * Upgrades are first tested on a separate/dedicated cluster to validate API deprecations and workload stability before upgrading existing production clusters.
